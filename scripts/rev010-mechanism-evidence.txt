# REV-010：定向删除 destination cache 的结果与真实机制判定
time : 2026-11-12 21:35:01
host : DESKTOP-E9ERP1I

## A. 已授权的定向删除确实执行成功，但对路由判定无效
  cmd    : netsh interface ipv4 delete destinationcache interface=10 address=26.187.101.177
  result : rc=0 ，控制台输出「确定。」
  after  : 26.187.101.177 = if=10 kind=DEFAULT-GW nextHop=192.168.31.1 metric1=45   <-- 仍为 WLAN

## B. 决定性对照：从未访问过的地址复现同样翻转
  probe target : 26.187.101.190（此前无缓存条目，neighbor=Unreachable）
  时间序列（首次实时观测，逐次记录）：
    initial       : if=18 on-link   nextHop=0.0.0.0        neighbor=Unreachable
    ping #1 期间   : if=18 on-link   nextHop=0.0.0.0        neighbor=Incomplete  100% loss
    ping #1 后0.7s: if=18 on-link   nextHop=0.0.0.0        neighbor=Incomplete
    ping #2 期间   : if=18 on-link
    ping #2 后0.7s: if=10 DEFAULT-GW nextHop=192.168.31.1  <-- 翻转发生在此
    ping #3       : if=10 DEFAULT-GW（保持）
  说明：翻转发生在邻居解析持续失败之后，不是首次发包即发生。

## C. 控制组：ARP 可达或未被探测的地址不翻转
  26.197.96.55  (VM，ARP=Stale 且有真实 MAC) 连 ping 4 次后 : if=18 on-link
  26.187.101.179(无应答，但从未被探测)                      : if=18 on-link

## D. 机制结论（推翻先前「destination cache 污染」假设）
  当 on-link 邻居的 ARP 解析持续失败（Incomplete）时，Windows IPv4 放弃该 /8 on-link 路由，
  回落到次优路由——if10 WLAN 的默认网关 192.168.31.1。
  这是「邻居不可达 -> 路由回退」，不是缓存污染；删缓存后重新推导，结果相同（A 段实证）。
  先前把 .177 的特殊性归因于缓存，是因为缺少两项对照：
    ①从未访问过的新地址是否也会翻转（B 段：会）
    ②ARP 有应答的地址是否不翻转（C 段：不翻转）

## E. 对 REV-009 条件 5 的直接影响
  只要 PC-B 26.187.101.177 不回应 Radmin 二层 ARP，该地址就必然回落到 if10。
  因此任何针对它的 DryRun 都无法得到 keep=if18 —— REV-009 条件 5 在其字面形式下不可达。
  这不是 helper 或编排器的缺陷，而是 peer 在 Radmin 二层不可达的事实
  （与 REV-005 已记录的 ARP Incomplete 一致）。
  需审计决定：条件 5 是改为接受「Radmin 通路不通时的已知回退行为」，还是改用可 ARP 应答的 peer 地址。
