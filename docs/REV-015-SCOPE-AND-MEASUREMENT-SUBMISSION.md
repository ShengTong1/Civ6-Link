## 1. 事实基线

### 1.1 三条路线的注入形态（规范原文，A 级）

| 路线 | 出向 | 入向 | 是否注入 DLL |
|---|---|---|---|
| Design I | Hook `sendto`/`WSASendTo`，目标为广播或 Fake-IP 时**吞包**、返回成功 | Agent 用 `SO_REUSEADDR` bind `Fake-IP:62056`，发真实 loopback UDP | 是 |
| Design II | 同上 | Hook `recvfrom`/`WSARecvFrom`/`select`，队列注入 | 是 |
| Design III | 依赖 H5（本机广播回环）+ `IP_PKTINFO` 捕获 | 同 Design I | 否 |

规范 §4.2 裁决标准：通过者优先级 `I > II`；III 若同样通过则列为推荐路线。

**已确认**：最终形态以注入为主选（Design I/II），Design III 是实验分支。负责人的理解与文书一致。

### 1.2 关键事实：入向在"同 LAN 直连"下不需要任何 Hook（B 级推理 + C 级实测支撑）

原生发现的双向过程（`M0A` E2-A 实测）：

- 客户端向 `255.255.255.255:62900..62999` 发 100 包 4 字节（E1，A 级）；
- 客户端**不 bind 62900**，它用同一个临时端口（E2-A 实测 `53787`）收回复；
- 房主从 `192.168.31.59:62900` 向客户端 `192.168.31.214:53787` 发 22 个 1104 B **单播**（E2-A，A 级）；
- 客户端显示房间列表项（E2-A + P2 合成实验，A 级/受限表述）。

→ **入向原本就是"定向单播打到一个已在监听的 socket"，客户端内核原生处理，不需要 Agent 介入、不需要 Fake-IP、不需要 `SO_REUSEADDR` 绑定。**

规范要求入向 bind `Fake-IP:62056` 的前提是**对端真实地址不可见或不可用**（跨网场景）。同 LAN 下对端真实 IP 可见且可用，这个前提不成立。

**边界**：本节是推理，不是实验结论。若审计端要求，可设计一个最小实验（A 机 Agent 手工向 B 机客户端临时端口发 22 页单播）来验证——但它的形态与 P2 合成实验几乎相同，而 P2 已证明"本机构建接受合成公告并显示列表项"。

### 1.3 同 LAN 下 Fake-IP / Relay / E2EE 的必要性存疑（B 级推理）

首版场景（同 WLAN、双人）中：

- 发现：客户端 Agent ↔ 房主 Agent 可直接 UDP 单播，双方真实 IP 互见；
- 数据面 62056：客户端原生就是向房主**真实 IP** 发单播（F3），不经广播；
- 因此 Fake-IP 映射、Relay 中继、E2EE 双层密钥在**这个场景内没有必须存在的理由**。

它们的存在理由在跨网：对端不可直连、需要隐藏拓扑、需要穿越 NAT。

**这与 REV-014 已批准的方向一致**：REV-014 批准的 `S1` 形状就是"直连助手（无 Hook/无 Relay）"。也就是说，路线图上本来就有这条线，只是它被标为"非发布原型"。

### 1.4 `T_window` 与实际是否收到响应无关（A 级实测对照）

| 数据源 | 有响应？ | 每轮 `T_window` |
|---|---|---|
| E1 真实日志（3 轮，`recvfrom=0`） | 否 | 2021.252 / 2018.945 / 2013.841 ms |
| P2 合成响应（3 轮，每轮 22 页） | 是 | 2016.987 / 2024.513 / 2018.729 ms |

两组不可区分。**结论：客户端发现 socket 的存活时长由游戏自身逻辑决定，与是否收到回复无关。**

推论（对测量必要性的直接影响）：**`T_window` 的获取不依赖广播是否成功到达对端，因此不依赖 metric 是否正确。**

而 `T_response` 才需要真实响应。P2 已用本机合成响应取得 74.182 / 13.997 / 15.170 ms——虽非跨机，但同 LAN 真实 RTT 是亚毫秒级，量级上不改变"H6 时间预算是否够用"的判断。

### 1.5 metric / 广播出口的定位（已被执行端降级，见 `METRIC-PRECONDITION-20261113.md`）

执行端 2026-11-13 已自行把该文档从"前置条件 + 待授权"降级为"环境观测记录"，理由：

- 当前无任何在办工作依赖它（S1 Phase 0 完全离线）；
- 产品形态（Design I 吞包）下，Windows 广播选路不发生；
- 由 §1.4，连 `T_window` 测量也不需要它。

**保留的唯一用途**：测量**原生基准**时（E2-A/E2-B/E3），要让"原生行为"包含真实到达对端的响应，需要广播路径正确。这是夹具条件，不是产品条件。

## 4. 请求裁定的事项

**D1．首版的价值主张（单选）**

- (a) **修复广播失效**：同 WLAN 下因虚拟网卡抢广播、AP 客户端隔离、防火墙等原因导致房间看不到；CivLink 用 Agent 间定向单播替代广播；
- (b) **跨网联机**：把同 LAN 玩家扩展到不同网络（这才需要 Fake-IP/Relay/E2EE）；
- (c) 两者都要，但必须分阶段，首版只做其中一个。

请求：明确 (a)/(b)/(c)，并说明另一个的方向。

**D2．若选 (a)：首版是否还需要 Fake-IP / Relay / E2EE？**

执行端观察：同 LAN 双人场景下三者都没有必须存在的理由（§1.3）。若审计端同意，首版形态可收窄为：

> Hook `sendto` 捕获游戏的发现广播 → 经 Agent 间 UDP 单播直送对端 → 对端 Agent 用自己缓存的 22 页公告，以**真实 IP:62900** 向客户端临时端口回单播 → 客户端内核原生接收、显示房间。

请求：确认或驳回该收窄。

**D3．若选 (a)：入向是否确认不需要 Hook 也不需要 bind？**

依据 §1.2。若确认，则：

- Design I 的"绑定矩阵 + 投递压测"（R1，规范标为"极高风险、M0-B 核心阻断项"）**在首版范围内可整体移除**；
- 首版唯一必需的 Hook 是**出向 `sendto` 捕获**（外加 H3 审计可能发现的其它出向路径）。

请求：确认该推论，或指出遗漏的攻击面（例如游戏是否校验回复源端口必须为 62900 区间、是否校验 TTL 等）。

**D4．`T_window` / `T_response` 是否仍按 Gate A 要求补真实跨机样本？**

依据 §1.4，`T_window` 已由 E1（无响应）+ P2（有响应）双路取得一致结果；`T_response` 目前只有本机样本。请求说明：E2-B 的真实跨机 `T_response` 是"必须补的证据"还是"已有本机样本即可裁定 H6"。

**D5．Design III 的处置**

若 D1 选 (a) 且 D3 确认入向不需要 Hook，那么唯一需要的 Hook 只是"捕获出向广播"。Design III 恰好用 H5（本机广播回环）替代这唯一一处 Hook——若能成立，产品**完全不需要注入**，F12 杀软门槛整体消失。

请求：是否值得把 H5 从"M0-B 内的一项"提前为独立实验？成本很低（本机 bind + 自发广播收包）。

**D6．对前次 REV-014 裁定的衔接**

REV-014 批准的 `S1` 形状（只读诊断 + 离线解析 + mock UI、无 Hook 无 Relay）与本文 §1.3 的收窄方向一致。请求说明：若 D1 选 (a)、D2 确认收窄，S1 是否从"非发布原型"升级为首版的形态基线，以及是否需要新的授权文书。
