## 1. 产品目标与稳定性目标

产品目标不变：**开房即玩**——房主点"创建房间"得到房间号，其他人输房间号即入，
不需要公网 IP、IPv6、端口映射，不需要理解 Fake-IP/UDP/Socket/NAT。

高稳定性验收口径（评审定义，全部为必须满足的产品级要求）：

1. 不同运营商、不同地区、不同家庭网络之间可稳定联机；
2. 2~8 人长时间稳定游戏；
3. 游戏更新、电脑休眠、网络波动之后能够恢复（隧道层恢复；游戏会话能否恢复以实测为准，见 §9.3）；
4. 不出现偶发搜不到房间、加入失败、游戏卡死、联机中途掉线；
5. 用户零网络配置。

**竞争力定位（评审原文）**：不是房间号，也不是 GUI，而是
"玩家不用研究网络配置，打开 CivLink 就能稳定地和朋友玩文明6"。

三原则（全文档强制）：
1. 不为了赶进度牺牲 Socket 兼容性；
2. 不为了降低延迟牺牲联机稳定性；
3. 没有经过真实游戏验证的功能，不进入正式发布版本。

## 3. 总体架构

控制面与数据面**彻底分离**（评审核心要求）：

```
 控制面 (WSS/TLS1.3): 注册房间·加入·认证·心跳·成员同步·密钥协商引导
┌────────────────────────────────────────────────────────────────┐
│                  Lobby Server (VPS, Rust+tokio)                 │
│                  不承载任何游戏数据                              │
└────────────────────────────────────────────────────────────────┘
                        ▲ 仅引导期交互（会话建立后 Lobby 失联不断游戏）
 数据面 (UDP+双层AEAD): 游戏流量交换
┌────────────────────────────────────────────────────────────────┐
│                  Relay Server (VPS, Rust+tokio)                 │
│          会话认证 · 密文交换 · 限速 · 统计 · 不解析载荷          │
└────────────────────────────────────────────────────────────────┘
        ▲UDP(双层加密)              ▲                ▲
 ┌──────┴───────┐            ┌──────┴───────┐  ┌─────┴────────┐
 │ Agent (Rust) │            │ Agent (Rust) │  │ Agent (Rust) │
 │ ┌──────────┐ │            │              │  │              │
 │ │hook.dll  │ │←— 本机 UDP —│  (同左)      │  │   (同左)     │
 │ │(Socket   │ │   127.0.1  │              │  │              │
 │ │ Adapter) │ │            │              │  │              │
 │ └──────────┘ │            │              │  │              │
 │ Civ6 进程    │            │ Civ6 进程    │  │ Civ6 进程    │
 └──────────────┘            └──────────────┘  └──────────────┘
     房主(固定)                    玩家B              玩家C
```

与 v1 的关键差异：
1. **Lobby 与 Relay 独立进程**：Lobby 短暂失联时，已建立的数据面会话继续工作（评审要求的
   "Lobby 失联不断游戏"）。VPS 自身故障仍中断游戏——备用 Relay 属 M4，第一版不做跨节点会话迁移。
2. **中继为全量转发**（评审：先全中继，打洞暂缓）。
3. 拓扑不写死：交换机按 `dstPeer` 转发，天然支持游戏实际的任何拓扑（星型或 mesh，见 H7）。

## 4. 本机注入路径设计（Socket Adapter）

### 4.1 Hook 层（C++ + MinHook，自研）

- Hook 集合**不预先固定为 7 个**。基线 7 个（F4/F5 已证实）：`bind`/`sendto`/`select`/
  `recvfrom`/`closesocket`/`WSASendTo`/`WSARecvFrom`；M0-A 的 API 审计（H3）若有增量
  （WSAPoll / WSAEventSelect / Overlapped 路径），按审计结果扩展最小集合。
- **线程安全规则（强制）**：Hook 内部只做查表/改写/入队，全部加锁保护；
  **Hook 路径上禁止任何阻塞式网络通信、禁止等待远端响应**（评审约束2）。
- 游戏主 socket 与 Agent socket 完全分离；Hook 的本地通道 socket 由 DLL 自建，与游戏无关。
- 非阻塞语义必须完整保留（F4）：替换/注入路径不得改变 socket 的阻塞属性与 WSAEWOULDBLOCK 行为。
- Steam 好友发现 47584 通道不得破坏（F10）。
- 日志：游戏目录 `civlink-hook-log.txt`（沿用 injciv6 的诊断思路），产品化为 GUI 诊断面板数据源。

### 4.2 数据交换路径：三条候选设计（M0-B 裁决）

评审约束1 要求回答：**Agent 的回包如何进入游戏 socket 的接收队列，select / 非阻塞
WSARecvFrom 如何正确报告可读**。三条路线全部在 M0-B 实测，按结果择优合入：

**Design I —— 发送 Hook + 回环注入（主选）**
- 出向：Hook `sendto`/`WSASendTo`。目标为广播（F1）或 Fake-IP（F7）时，**吞包**（不调原函数，
  返回成功），把 `[原始目的地址 | 载荷]` 经本机 UDP 交给 Agent（帧协议见 4.4）。
- 入向：**不经 Hook**。Agent 用 `SO_REUSEADDR` bind `Fake-IP:62056`（与游戏通配 bind 共存，
  依赖 H2），以 `Fake-IP:62056` 为源、`127.0.0.1:62056` 为目的发真实 loopback UDP；
  游戏 socket（通配 bind）原生收到，源地址即 Fake-IP，可读状态由内核原生维护——
  select / 非阻塞 WSARecvFrom 全部原生正确。
  发现回复注入同理：Agent bind `房主Fake-IP:62900`（客户端机无人占用 62900，无冲突），
  目的为游戏发现 socket 的 ephemeral 端口。
- 风险：H2 不成立（游戏 SO_EXCLUSIVEADDRUSE）时整条失效 → Design II。
- 优点：入向零 Hook，语义 100% 原生；实现量最小。

**Design II —— 全 Hook + 队列注入（兜底）**
- 入向：Hook `recvfrom`/`WSARecvFrom`/`select`（+审计发现的其它读路径）。
  Agent 把 `[原始源地址 | 载荷]` 发到 Hook 的本地控制端口；Hook 维护每游戏 socket 的
  接收队列：游戏调用 WSARecvFrom 时队列非空 → 出队并按帧内源地址填充 sockaddr 返回；
  队列空 → 返回 `WSAEWOULDBLOCK`（保持非阻塞语义）；select 时报告队列可读。
- 风险：异步通知路径（H3 若发现 EventSelect/Overlapped）实现复杂度高；`select` fd_set
  同步替换的正确性；这是 injciv6 的路线（已验证但仅限其场景）。
- 若 H3 审计发现异步路径 → 本设计复杂度上升，需重新评估。

**Design III —— 无 Hook 回环 shim（实验分支，若可行则 F12 杀软问题整体消失）**
- 出向依赖 H5（本机广播回环）+ 游戏向 Fake-IP 发包被 OS 路由到 loopback、Agent 以
  `recvmsg/IP_PKTINFO` 取目的地址识别 peer；入向同 Design I。
- 若 H5 成立且出向无需 Hook：**完全不注入、不挂 DLL**，产品形态退化为"Agent + 防火墙规则"。
- 已知缺口：出向广播是否可靠回环（H5）未证；发现包 4 字节定长、100 端口，捕获面需 bind
  多端口。作为对照实验与远期减负路线。

**裁决标准（M0-B）**：两台同 LAN 机器，游戏数据全部经本机 Agent echo 交换，发现+加入+开局
完整走通、与原生 LAN 联机行为一致、无卡死；多 peer Fake-IP 映射正确。通过者优先级
I > II；III 若同样通过则列为推荐路线（免杀软价值大）。

### 4.3 FakeEndpoint 映射（评审 P0-5）

v1 的 `peerId ↔ 127.0.127.x` 过于简化，重设计为五元组双向映射：

```
FakeEndpoint = { fake_ip, fake_port }          // 游戏视角的对端地址
PeerEndpoint = { peer_id, tunnel_session_id }  // 隧道视角的远端身份
绑定键 = 本地游戏 socket id + FakeEndpoint      // 同一 peer 多 socket/多端口各自独立

出向查表: Hook 收到游戏发包 (socket_id, dst=FakeEndpoint) → 对应 PeerEndpoint → 隧道封包
入向查表: Agent 收到隧道包 (peer_id, 原始源端口) → 分配/查询 FakeEndpoint → 注入
```

**上游教训**：injciv6 v0.3.3（2024-03-09 发布，GitHub Releases 原文已复核）更新说明包含"整理hookdll内代码，修复fake-ip分配问题"——分配/回收/并发是该类模块实际出过 bug 的地方，本节生命周期管理为**强制项**而非可选优化。

生命周期管理（全部强制）：
- 映射创建：首次发现流量或首次数据流量时分配 Fake-IP；
- 过期回收：无流量 10 分钟回收 Fake-IP 与绑定 socket；
- 清理：游戏 `closesocket` 联动清理该 socket 的绑定（injciv6 同款）；游戏进程退出全量清理；
- 同一 peer 多 socket：键含 socket id 与端口，互不串线；
- 端口冲突检测：Agent bind Fake-IP 失败时显式告警并降级（Design II），不静默；
- 游戏重启重建：映射表不持久化，重启后随发现流程自然重建。

Fake-IP 段选型（评审 P0-1）：**不拍板**。双候选：`127.0.127.1~127.0.127.100`（F7 实证）
与 `198.18.0.0/15`（H1 对照）；M0-B 以游戏实际收发的源/返回地址与 socket 行为实测裁决，
同时记录游戏对两者的兼容差异。

### 4.4 Hook ↔ Agent 本地帧协议（CVLH1）

本机 `127.0.0.1:34718` UDP，仅本机回环：

```
magic(4B)='CVLH' | ver(1B) | dir(1B: 0=hook→agent 出向, 1=agent→hook 入向[仅Design II])
| orig_addr(16B: family+IPv4/IPv6+port) | payload_len(2B) | payload
```

- 出向（Design I/II/III-hook 均用）：Hook 捕获游戏发包后按此帧交 Agent；
- 入向：Design I 走真实 loopback UDP（无帧）；Design II 走此帧交 Hook 队列；
- 本地通道丢包容忍：游戏协议自带重传（RFC 8085 立场，见 §6.2），本地 loopback 丢包率趋近 0。

## 6. 数据面与 Relay

### 6.1 职责边界（原则B）

Relay **只做**：验证会话身份（§8.5）、验证房间归属、按 `dstPeer` 转发密文、限速、统计。
**不做**：解析或修改游戏载荷、理解游戏协议、参与加密（见 §8.2 信任模型）。

游戏载荷在 Agent 侧零修改进出（除 §2 H4 裁决可能要求的"发现阶段地址字段改写"——
该改写只发生在发现阶段的 1104B JSON 上、只动地址字段、只由本机 Agent 执行；
**游戏数据面 62056 载荷 100% 原样**）。

### 6.2 流量分类处理策略（评审 P0-3）

| 数据类型 | 隧道处理策略 | 依据 |
|---------|-------------|------|
| 游戏原始 UDP（62056） | **透明转发，不擅自重传**。游戏协议可能已有可靠性机制，隧道层盲目重传会造成重复处理/额外延迟/拥塞 | RFC 8085；评审 P0-3 |
| 房间发现（62900~62999） | 可控转发 + Agent 侧超时重试（按发现周期重发） | F1/F2 |
| 心跳 | 定时发送、超时检测（进入 DEGRADED，不立即踢人） | §9 |
| 成员状态 | 可靠同步（走控制面），带版本号 | §7 |
| 房间创建/加入 | 请求 ID + 幂等处理（走控制面） | §7 |
| 密钥协商 | 可靠控制通道（走控制面引导） | §8 |
| 网络恢复 | 会话重建 + 成员状态同步 | §9 |

### 6.3 Relay 行为

- 会话表：`session_id → (peer_id, room_id, 对端地址, 密钥域L1, 统计)`；
- 身份绑定：包的 `srcPeer` 必须与 L1 会话推导的身份一致，不一致丢弃（评审 P0-6-3，见 §8.5）；
- 广播：`dstPeer=0xFFFFFFFF` → 房间内除源外全员；
- 限速：单会话令牌桶（防滥用），超限丢弃并计数；
- 统计：每会话包数/字节/重置计数，供 GUI 诊断面板与容量实测（§10.3）；
- NAT 重绑定：会话以 `session_token` 标识，源地址变化时凭 token 重新挂载，seq 连续性不中断（§9.2）。

## 7. 控制面与 Lobby

### 7.1 通道

WSS（TLS 1.3，端口 8443）。消息 JSON（控制面流量小，不追求二进制紧凑）。

### 7.2 房间模型

- `roomId`：6 位数字；**可选房间密码**（4~8 字符，评审要求）；
- 防枚举：加入请求按源 IP 限速 + 连续失败锁定；密码错误计数告警；
- 成员表：`peerId（设备密钥派生）、昵称、状态、加入时间`，版本号单调递增，变更推送 + 全量同步；
- 心跳：Agent 15s 间隔；5 分钟无心跳回收房间（沿用 v1，但踢人前先走 §9 DEGRADED 流程）；
- 密钥协商引导：建房时 Lobby 生成房间票据与成员名单，Agent 间 E2E 握手经数据面完成（§8）。

### 7.3 房主策略（原则A）

- 第一版**固定房主**：房主创建房间；其他玩家加入；**房主离开 = 房间关闭**（所有成员收到
  明确提示，不静默）；
- 不做房主迁移——文明6 原生游戏会话的主机迁移能力不能由 UDP 中继自动提供，
  核心链路稳定后再评估；
- "全员对称"从 v1 卖点降级为**远期目标**：任何家宽玩家都能当房主（无需公网）这一点保留，
  但"房主可更换"暂缓。

### 7.4 降级原则

Lobby 失联：已建立的数据面会话继续工作（§3）；Lobby 恢复后重新同步成员状态。
Lobby 长时间失联：禁止新加入/新房间，进行中的游戏不受影响。

## 8. 加密协议（评审 P0-6 全量重设计）

### 8.1 密码学选型

| 用途 | 选型 | 备注 |
|------|------|------|
| 控制面传输 | TLS 1.3（WSS） | 成熟基础设施 |
| 数据面会话密钥协商 | **Noise 协议框架**（Noise_XX 起步；Relay 静态密钥可固化后升级 Noise_IK） | 经审查的模式，不自研握手 |
| 数据面 AEAD | **ChaCha20-Poly1305**（IETF 变体，12B Nonce） | 备选 AES-GCM |
| 密钥派生 | Noise 内建 HKDF | 不自研 KDF |

### 8.2 信任模型（统一，替代 v1 的混用描述）

**双层密钥域，端到端加密（E2EE）**：

- **L1（Agent ↔ Relay 传输会话）**：Noise_XX 握手建立会话密钥 → 外层信封 AEAD。
  作用：Relay 验证发送者身份（§8.5）、防篡改路由头、防伪造；
- **L2（Agent ↔ Agent 端到端）**：房间成员两两 Noise_XX 握手（握手消息作为数据面载荷经
  Relay 中转，Relay 不可读），游戏载荷 L2 加密。
  作用：**Relay 只见密文**，无法读取游戏数据、无法伪造（L2 认证失败即丢）、无法重放（窗口）。

L1/L2 相互独立：L1 密钥泄露不暴露载荷；Relay 被攻破只等于"可丢包/延迟的哑管道"（DoS 面，
明示为接受的风险）。**Relay 解密再加密模式不采用**，全文档以此为准。

### 8.3 Nonce 规则（修复 v1 的 8B Nonce 缺陷）

- 96-bit（12B）Nonce，符合 ChaCha20-Poly1305 IETF 标准；
- 每 L1/L2 会话密钥独立：`nonce = direction_bit(8b) || counter(88b)`，从 0 单调递增，
  同一密钥下永不重用；
- 重连/重换密钥 = 新会话 = 新密钥（Noise 握手产生全新密钥），**不存在跨会话 Nonce 重用问题**
  （v1 的 `nonce=seq||srcPeer` 方案作废）；
- 密钥轮换：计数到达 2^48 或会话存活超 24h 触发重协商，**Epoch +1**，新旧 Epoch 短暂并行收包。

### 8.4 头部认证与重放保护

- 外层信封：`header(roomId|srcPeer|dstPeer|seq|epoch) + AAD` 纳入 AEAD 认证，
  篡改任一字段 = 解密失败 = 丢弃；
- **重放窗口**：每个会话每方向维护 1024 位滑动窗口，窗口外旧 seq 直接丢弃
  （Relay 层与 Agent 层各一道）；
- seq 单调递增，NAT 重绑定/会话恢复不回退（§9.2）。

### 8.5 身份绑定（修复"仅凭客户端上报 srcPeer"缺陷）

- Relay 不信任信封里的 `srcPeer`：发送者身份由 **L1 会话推导**（会话表 `session → peer_id`），
  信封 `srcPeer` 仅作一致性校验，不一致即丢；
- `dstPeer` 路由基于成员表校验（该 peer 必须在房间内且会话有效）；
- L2 层由 Noise 握手身份（设备密钥）再次绑定，双重保障。

### 8.6 测试要求

标准测试向量（RFC 8439）、Noise 官方测试向量、重放攻击用例、篡改用例、Epoch 切换用例——
全部进 CI（评审原则C）。

## 9. 网络状态机与故障处理

### 9.1 Agent 状态机

```
DISCONNECTED → CONNECTING → CONNECTED → IN_ROOM → IN_GAME
                    ↑                      ↘        ↙
                    └──── RECONNECTING ← DEGRADED ←┘
（CONNECTED = 已认证等待加入；IN_ROOM = 成员同步完成；IN_GAME = 游戏数据正常转发）
```

状态机不是状态显示，是**异常处理策略的调度器**——每种异常的应对方式如下表。

### 9.2 异常处理矩阵

| 异常 | 检测 | 应对 |
|------|------|------|
| Lobby 短暂失联 | WSS 断开 | **保持已有 Relay 会话与游戏转发**；指数退避重连；恢复后同步成员表 |
| Relay 心跳丢失 | 数据面 15s 无包 | 进入 DEGRADED：保留会话继续尝试发送，30s 后 RECONNECTING；**不立即踢人** |
| NAT 映射改变（源地址变化） | Relay 观测到同 token 新地址 | 凭 session_token 重挂载（§6.3），seq/Epoch 连续，无需重新握手 |
| 玩家网络切换（Wi-Fi↔有线/IPv4 漂移） | Agent 本地探测 | 同上重绑定；失败则 RECONNECTING |
| Agent 崩溃 | 进程守护 | 自动重启 → 重新注入 → RECONNECTING → 凭 token 恢复会话 |
| 游戏异常退出 | 注入进程监测 | 清理 Socket/Fake-IP 映射与本地通道，状态回 CONNECTED，GUI 提示 |
| VPS 重启 | Relay 全量断开 | 会话丢失不可自动迁移（§3）；Lobby 通道若存活则明确通知"房间已中断，请重新建房"——**不静默假装恢复** |

### 9.3 隧道恢复 vs 游戏会话恢复（评审特别强调）

- **隧道恢复**（Agent↔Relay 连接重建、成员映射恢复）：由本设计保证；
- **游戏会话恢复**（文明6 能否在底层断连后无缝继续原局）：**未验证，不承诺**。
  文明6 正在进行中的游戏对底层中断的容忍度未知（关联 H12）。M2 实测给出结论：
  能/不能/何种中断时长内能。产品文案按实测结果措辞，不夸大。

### 10.2 量化验收指标

> 定位说明：Relay 额外延迟指**本系统新增**延迟；端到端延迟是玩家间真实网络延迟，
> 两者分开考核，不为延迟指标盲目上打洞（评审）。

| 指标 | 目标值 | 性质 |
|------|--------|------|
| Relay 本身额外延迟 | P95 ≤ 30ms | 目标 |
| 数据面丢包率 | ≤ 0.1% | 测试目标 |

| 8 小时运行稳定性 | 无隧道故障 | 必须 |
| 房间发现成功率 | ≥ 99.9% | 测试目标 |
| 房间加入成功率 | ≥ 99.5% | 测试目标 |
| Agent 内存泄漏 | 不持续增长 | 必须 |
| Socket 泄漏 | 无 | 必须 |
| 异常退出后资源清理 | 100% | 必须 |

### 10.3 容量模型（替代 v1 已删除的估算）

出口流量近似 `B_out ≈ N(N-1) × R`（R=单玩家平均发包速率，全员广播扇出 N-1）；
**R 与广播/单播比例必须 M0-A 实测**（Wireshark 统计原生局的包频率/包长/方向矩阵），
服务器规格以实测数据推导，**设计阶段不再给出带宽数字**（评审否决 v1 估算）。

### 10.4 VPS 初期规格

2 vCPU / 2 GB RAM / 充足 UDP 带宽与流量额度 / 独立监控 / 独立日志 / 固定公网 IPv4。
先用此规格压测，再按数据调整。优先级排序（评审）：VPS 网络质量 > 与玩家 RTT >
UDP 转发性能 > 丢包与突发拥塞 > （M4）双节点容灾。

M0 各实验**不允许只记录"是否联机成功"**，全程记录以下观测项（采集方法见工具包手册 §8）：

## 14. v1 → v2.0 修订摘要

1. 协议章重构：F1~F13 已证实事实 + H1~H13 待验证假设分级，v1 两处误读修正
   （"端口动态"实为目标端口循环 62900~62999；"星型拓扑"降级为待验证 H7）；
2. 新增三候选注入路径（Design I/II/III）+ CVLH1 本地帧协议，回包入队问题有明确答案；
3. Fake-IP 映射升级为 FakeEndpoint 五元组 + 完整生命周期；选段改实验裁决；
4. 加密全量重设计：双层密钥域 E2EE、Noise、12B Nonce、AAD 头部认证、重放窗口、身份绑定；
5. 控制面/数据面分离为独立进程，Lobby 失联不断游戏；
6. 新增 7 态网络状态机 + 异常处理矩阵；隧道恢复与游戏会话恢复明确区分；
7. 里程碑重构 M0-A/B/C，M0-B 为技术闸门；每阶段带验收标准；
8. 删除无依据带宽估算，改实测前置；量化验收指标表落地；
9. 第一版固定房主（原则A），全员对称降为远期目标。
