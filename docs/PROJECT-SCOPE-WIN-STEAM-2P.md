# CivLink 首版范围决议与阶段计划

- 决议日期：2026-11-12
- 决策人：项目负责人
- 状态：**当前有效范围决议**
- 依据：项目负责人明确决定首版限定为 **Windows + Steam + 双人**
- 基准设计：`CivLink-技术设计规范-v2.1.md`

## 1. 首版承诺

首版只承诺：两名玩家在 Windows 上运行 Steam 版《文明6》，通过 CivLink 创建/加入房间并完成双人联机。初期实验固定一台房主、一台玩家；构建、DLC、网络条件均记录并保持可比。

首版**不承诺** Epic/Win64EOS、三人及以上、8 人规模、房主迁移、跨版本兼容矩阵或长时间稳定性指标。它们保留为后续版本工作，不得用双人结果宣称已经验证。

## 2. 架构决策状态

产品不是单独一个 DLL。v2.1 的目标组件是游戏侧适配层、独立 Agent，以及 Lobby/Relay 服务。游戏侧适配层目前有三种候选路径：

| 路径 | 是否向 Civ6 注入 DLL | 状态 |
|---|---|---|
| Design I：发送 Hook + Agent 回环投递 | 是 | 候选主路，需 M0-B 绑定/投递确定性实验 |
| Design II：收发 Hook + 显式接收队列 | 是 | 兜底候选，需处理 H3 审计发现的接收模型 |
| Design III：无 Hook 的 Agent shim | 否 | 实验分支；只有发现与数据面都实测可行才可采用 |

`civtrace.dll`/`civinject.exe` 是 M0-A 观察工具，不是上述任一产品实现。最终是否注入 DLL 由 M0-B 实验裁决；即使采用 Hook，Agent、Lobby 和 Relay 仍是独立组件。

## 3. 对 v2.1 的范围修订

本决议只裁剪首版验收范围，不抹去 v2.1 的长期目标和技术风险。发生冲突时：本文件决定首版支持范围与首版 Gate A；v2.1 继续提供技术设计、实验方法和后续版本要求。

| 原规划项 | 首版处理 | 原因/边界 |
|---|---|---|
| H3：游戏 I/O 模型及旁路 API | **保留为首版 Gate A 阻断项** | Hook 若漏掉真实收发路径可能漏包或卡死 |
| H4：发现回复是否在载荷含地址 | **保留为首版 Gate A 阻断项** | 决定是否必须改写发现 JSON 地址 |
| H6：发现窗口与响应时序 | **保留为首版 Gate A 阻断项** | 决定 Agent/Relay 往返能否赶上游戏窗口 |
| H8/H10：62056 socket 选项与生命周期 | **保留为首版 Gate A 阻断项** | 决定 Hook 和 FakeEndpoint 的边界 |
| H7：三人 mesh/star 拓扑 | 从首版 Gate A 移出，列为后续验证 | 双人拓扑不需要推断第三名玩家的转发关系 |
| H11：三人及以上加入缺陷 | 从首版 Gate A 移出，但列为明确产品限制/后续风险 | 首版最多两名玩家；不得宣称 3+ 支持 |
| E4 三机五轮实验 | 延后至多人版本 | 当前资源最多两台 Civ6 电脑，且该实验不是双人验收的必要条件 |
| E5 Win64EOS | 首版不支持，延后 | Steam 结果不代表 EOS；首版只支持 Steam |
| InterfaceMetric/Radmin 根因及 metric helper 往返 | 不属于首版技术 Gate | 网络诊断/临时 workaround 可单独审计，不证明 Hook、Fake-IP 或 Relay 可行 |

### 首版 Gate A（M0-A 完成标准）

以下各项须有可复核的本机证据；口述结果可作为线索，不单独作为通过依据：

- [ ] PC-A、PC-B 的 Windows/Steam Build ID、游戏二进制哈希、DLC 和网络环境基线可比。
- [ ] E1 的 F1 发现广播在本机抓包中复证；注入/原生对照范围与证据限制清楚。
- [ ] E2-A 逐轮记录两端 PID、房主/客户端角色、注入状态、刷新时刻与捕获窗口；至少取得可解释的房间响应和原始发现回复样本，完成 H4 被动字段分析。
- [ ] E2-B 取得 H6 的 `T_window`/`T_response` 样本分布及发现 socket 生命周期素材；有响应与无响应轮次均保留。
- [ ] E3 在两台真实 Steam Civ6 端完成双人发现、加入和进入对局的基线观察；对 62056 socket 归属 H3/H8/H10，包含 Overlapped、事件、扩展函数和 IOCP 排查。
- [ ] 广播与单播的观测分开统计；civtrace 对时序/行为的影响有对照记录，异常不被静默排除。
- [ ] 对“Radmin 源”只报告源地址/捕获接口等直接观察；在 Radmin 客户端下线的事实下，不把残留虚拟网卡解释成在线 VPN 隧道，也不把 InterfaceMetric/ARP 机制写成已证实因果。

**首版 Gate A 不要求** E4/H7/H11 或 E5/EOS。它们的状态必须记作“超出首版范围/未验证”，不是“通过”。

### 首版 Gate B（M0-B 开始标准）

首版 Gate A 通过后，M0-B 在两台 Windows Steam 电脑上验证：

- H1 的 Fake-IP 候选段实验（来源地址过滤、本机绑定/发送、回环注入分别裁决）；
- H2 绑定组合与顺序矩阵，以及 Design I 的至少 1000 次带序号投递确定性压测；不确定则转 Design II；
- H5 本机广播回环能力，和 Design III 可行性；
- Hook↔Agent 本地通道的可靠对账、非阻塞语义和发现双向注入完整路径；
- 两台真实游戏端完成发现、加入、开局；重复测试无卡死、接收路径残留或无法解释的数据丢失；原生 LAN 行为仍可用。

Gate B 不通过时，不把实验 Hook 合并为正式产品，也不宣称可联机。

## 4. 开发计划与可并行范围

### 当前阶段：完成双人 Steam 的 M0-A

1. 将执行端报告的“五次刷新：一次 WLAN 成功、四次 Radmin 源失败”原始日志、双端抓包、哈希和逐轮表归档；当前先标“项目负责人提供的观察，待复核”。
2. 补齐/复核 E2-A 房主回复与 H4 样本；不得以广播到达代替房间发现成功。
3. 执行 E2-B 与 E3；E2-B 与 E3 均使用全新游戏进程，按工具契约记录注入和停用状态。
4. 汇总首版 Gate A 矩阵，逐项标注源码确认、抓包/日志确认、推断、未验证，再提交审批。

### 可提前开展的独立工程原型

为避免把“游戏 Hook 未裁决”扩大成“所有代码停工”，可以单独建立非发布原型：Rust workspace/Agent 服务骨架、Relay 原始数据转发 harness、模块接口和本地模拟测试。边界如下：

- 不注入 Civ6，不拦截/改写真实游戏流量，不宣称 M0-B 通过；
- 不冻结最终 wire format、身份/密钥协议或 Fake-IP 地址段；加密选型仍按 v2.1 后续决策执行；
- 原型与产品发布分支隔离，待 M0-B/M0-C 相应 Gate 通过后再决定合并。

该并行原型是降低排队浪费的建议，不会替代 M0-A/M0-B 验收，也不授权修改真实网卡 metric。

## 6. 权威文档与协作规则

1. 本文件是首版范围与阶段验收的当前权威补充。
2. `docs/CODEX-HANDOVER-M0A.md` 是执行端唯一当前交接入口；每次阶段变化先更新它。
3. `README.md` 是 M0-A 操作手册。早期 PC-B 操作单/交接文档已标为过期，不得直接执行。
4. `REV-005-E2A-REVIEW.md` 撤回 E2-A 的“InterfaceMetric 唯一原因”“ARP 首包机制”等结论；后续报告不得从旧 README 复制这些说法。
5. 证据报告应区分：直接抓包/日志事实、源码事实、基于事实的解释、口述待复核和未验证事项。
6. Gate 状态只由正式复核更新。范围缩小不会自动批准 Gate A/B，也不会自动把推断变成验证结论。
