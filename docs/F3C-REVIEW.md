## 0. 总结论（先给结论）

1. **证据本身是真的。** 10 个证据文件的 SHA-256 与文档 §6 表格**逐条相符**；10 个载荷的 SHA-256 由本审计用 .NET `SHA256` 独立复算，与 Agent 侧两处记录**三方全等（10/10）**；9 个退避间隔由本审计从 `forward-log.txt` 时间戳独立重算，与文档 §4 **完全一致**。这三项是本轮最硬的资产，不是"文档说通过"，而是可以复现的算术事实。

2. **但"23/23 通过"这个数字被高估了。** 23 次 `Check` 调用确实存在（本审计逐行计数，精确为 23，见 §E.5），但其中相当一部分断言在本夹具下**没有鉴别力**：
   - 断言 7（`skip not datapath == 0`）与断言 8（`skip key table == 0`）所对应的分支**在本实验里从来没有被执行过**——10 帧全部是 `dst=62056`，且只用了 1 个映射键。这两个"0"只证明"分支没被走到"，不证明"分支逻辑正确"。
   - 断言 14/15/16（缺口/重复/重排全 0）在"脚本按 1..10 严格递增发送"的夹具下近乎结构性成立；且重复/重排计数只覆盖**入向**（Agent 收包侧），转发到对端之后的重复**完全没有计数器**。
   - 断言 11/12/19/20/21 与断言 4/5/10 是同一批计数的不同投影。
   - 真正具备独立鉴别力的断言大约只有 6 条：2（退出码）、4+5（转发计数与字节）、10+11（对端接收计数与字节）、14（缺口，能看见丢帧）、22（sha256 三方对账，**最强**）、23（时间间隔）。

3. **断言 13 名不副实。** 文档 §3 把它写成"对端首个发送者 == Agent 的转发 socket"，但它实际只比较两个日志字段**冒号后的十进制尾数**（脚本 `:217-220`）。`forward sock` 是绑定地址 `0.0.0.0:55018`，`first sender` 是实际源地址 `127.0.0.1:55018`——IP 部分本就不同，脚本因此**回避了 IP 比较**，也没有用 `Get-NetUDPEndpoint` 反查 PID。它证明的是"两个日志字段的端口数字相同"，不是"投递被绑定到本进程的转发 socket"。

4. **断言 17 的结论越界。** "不重传"在**原理上不由** `forwarded == peer received` 证明。这个等式只说明"发了 10 个、收了 10 个"。接收端（`ForwardListener::drain`）**没有任何去重逻辑**——这是对本实验有利的事实，它排除了"重传了但接收端丢了重复包"这一种情况；但它无法排除"重传发生 + OS 缓冲恰好丢掉等量包"的组合，也无法排除"重传代码存在但路径从未被走到"。**真正的证据在代码里**：`main.rs:757` 每个接受帧只调用一次 `sock.send_to`，没有重试循环、没有补偿发送。文档没有引用这条代码证据，反而用一个较弱的运行期等式去承担结论。

5. **被审工件在审计期间被改写。** `civlink\civlink-agent.exe` 与 `civlink\agent\src\main.rs` 在本审计的 14 分钟内至少变了 3 次（详见 §A.1）。文档 §6 "文件身份（SHA-256，实测）"里 `main.rs` 一行**从头就是错的**（写的 76,311 是抄自 `docs\F3A-REVIEW.md:53` 的整改前旧值），`exe` 一行**现在已经不匹配**。这不是文档作者撒谎——14:59 首次测量时 exe 确实还是 `563122E2…`——而是"证据 ↔ 二进制"的链条没有被冻结。

6. **夹具与 S5 不是逐字节对应。** 除文档已声明的"载荷逐字节抄自 S5"之外，还有 **2 处未声明的差异**：`src` 字段（S5 是 `0.0.0.0:62056`，F3-C 硬编码 `127.0.0.1:21345`）与 `session_id`（S5 是 `0xaf8a2794b6d7`，F3-C 硬编码 `0x1`）。这两处差异不影响"转发不改载荷"的结论（载荷与长度确实一致），但"逐字节对应 S5"这个说法不能原样成立。

7. **最小结论。** F3-C **足以**支撑一个很窄的结论："在本机回环、单会话、单映射键、8 字节载荷、0.5–128 s 间隔的条件下，10 帧退避序列原样、按序、一帧一次地穿过本原型的转发链路。"它**不足以**支撑文档标题语境下的"退避语义在转发链路上不被破坏"这一较强结论——后者至少还需要一条负向对照实验（见 §F.2）。

- 脚本 `:126-130`：`$onDatapath = Get-NetUDPEndpoint -LocalPort 62056 -ErrorAction SilentlyContinue`，`$agentOn62056 = @($onDatapath | Where-Object { $_.OwningProcess -eq $proc.Id })`，断言 `$agentOn62056.Count -eq 0`。

- 更关键：这可能是**瞬时采样**。脚本在 Agent 启动后立即取一次快照，此后 258 秒运行期间**没有再采样**。若 Agent 在运行中后绑定 62056，本次断言完全看不见。
- 该断言**并非完全恒真**——如果 Agent 真的绑定了 62056，`$onDatapath` 会非空且 `OwningProcess` 匹配，断言会失败。所以它捕捉的是"Agent 是占用者"，但**不能区分"无人占用"与"Agent 未占用"**，也不能覆盖运行全程。文档 §3 第 1 行写"Agent 不绑定 UDP :62056"，实测列写 `owned endpoints=0`，措辞比断言实际能证明的更强。

**关于断言 18 的专项分析（F3C-R-10）**

- `$summary -match 'LOOPBACK PROTOTYPE'` 只依赖 Agent 的固定文案（`main.rs` 的 notes 段与本报告 §2 快照中的 `:1720`）。
- 这个字符串**由被测试程序自己打印**。断言"程序打印了'这是回环原型'"，与"这个实验确实是回环"之间没有推理关系。把被审对象的自我声明当作断言，是典型的自证。它唯一的作用是：如果哪天有人删掉这行 notes，测试会红。这不是一条关于实验性质的断言。
- 文档 §3 第 18 行"summary 声明回环原型边界 / 含 `LOOPBACK PROTOTYPE`"的措辞本身是**准确的**（它确实只说"声明"），所以这是断言设计问题，不是文档陈述问题。但把它计入"23 项通过"，会抬高读者的信心。

**关于 `Grab` 空串假通过的风险（B.1e，委托明确要求检查）**

- `:178-182 function Grab` 在正则不匹配时 `return ''`。
- 本脚本的 12 个 `Grab` 结果全部与**非空字面量**比较（`'10'`、`'80'`、`'0'`、`'1'`、`"$peerPort"`）。PowerShell 中 `'' -eq '0'` 为 `$False`，故**正则失败会导致断言失败（fail-safe）**，不会产生"空串当成 0 而假通过"。
- **这一点与 F3-A 的已知问题不同，F3-C 在此处是安全的。** 但有一个仍然存在的隐患：`$sockPort`/`$senderPort` 在正则失败时也是 `''`，而断言 13 有 `$sockPort -ne ''` 守卫，所以即便两个字段都解析失败，断言会失败而非通过——安全。
- 结论：`Grab` 的空串行为在 F3-C 中**没有造成假通过**，属于"已规避的历史坑"，不需要修改，但建议在脚本注释中写明"所有 Grab 结果必须与非空字面量比较"，以免后续维护者引入 `-ne 0` 之类的放宽写法。

### B.2 断言 13 的专项判定（委托 B.2）

**问题：这个断言是否真的把投递绑定到了本进程的转发 socket？**

**答：没有。**

脚本 `:215-220` 的实际逻辑：

```
$fwSock      = Grab $summary 'forward sock\s+:\s+(\S+)'      # -> "0.0.0.0:55018"
$firstSender = Grab $summary 'first sender\s+:\s+(\S+)'      # -> "127.0.0.1:55018"
$sockPort    = 取 $fwSock 最后一个冒号后的数字   # -> "55018"
$senderPort  = 取 $firstSender 最后一个冒号后的数字  # -> "55018"
Check ... ($sockPort -ne '' -and $sockPort -eq $senderPort)
```

四点判定：

1. **只比端口，不比 IP。** 脚本用 `:(\d+)$` 抓取，主动丢掉了 IP 部分。这不是疏忽，而是**必须**——因为 `forward sock` 打印的是绑定地址 `0.0.0.0:55018`，`first sender` 打印的是实际源地址 `127.0.0.1:55018`，两者 IP 天然不同（`main.rs:689` 绑的是 `0.0.0.0:0`，环回目标使 OS 选 `127.0.0.1` 作为出包源）。**因此即使脚本想比 IP 也比不了**，除非改成比较"解析后的实际源地址"。

2. **端口匹配可能被另一个进程偶然命中吗？** 概率低但非零。55018 落在 Windows 动态端口段 49152–65535。同一台机器上若存在另一个进程（或同一个 Agent 的另一次运行、或上一个未退出的 Agent 实例）恰好占用 55018，并且它也在向 21347 发包，则 `first sender` 也会是 `127.0.0.1:55018`，断言照样通过——**而那个包不是本进程发的**。本实验之所以没出问题，是因为 21347 由本进程独占监听（脚本 `:46-50` 会检查占用），所以只有本进程能收到包；但脚本**没有把这一层"监听独占"与"发送方是同一进程"关联起来**。

3. **没有做 PID 反查。** 正确做法是：解析出 `55018` 后执行 `Get-NetUDPEndpoint -LocalPort 55018 | Select-Object OwningProcess`，断言该 PID 等于 `$proc.Id`。这才能把"端口"升级为"进程"。当前脚本完全没做。

4. **结论**：断言 13 证明的是"`summary.txt` 第 32 行与第 45 行冒号后的十进制数字相同"。这是一个**字符串层面的巧合检查**，不是进程层面的身份绑定。文档 §3 第 13 行"**对端首个发送者 == Agent 的转发 socket**（端口一致）"中的"（端口一致）"是诚实的限定，但标题部分（"== Agent 的转发 socket"）读起来像是身份等价，实际不是。

**修法（最小改动）**：在脚本中把断言 13 换成三条并联（任一失败即红）：

```
$fwPort = 从 forward sock 解析出的端口
$e = Get-NetUDPEndpoint -LocalPort $fwPort -ErrorAction SilentlyContinue
($e | Where-Object { $_.OwningProcess -eq $proc.Id }).Count -eq 1        # 端口确实属于本进程
$firstSenderIp -eq '127.0.0.1'                                          # 源 IP 是环回
$senderPort -eq $fwPort                                                 # 端口一致（现有）
```

**更强做法**：让 Agent 在 summary 中额外打印 `forward sock local_addr()` **与** `forward sock 实际出包源地址`（可用 `connect()` 后 `local_addr()` 取得），再断言 `first sender == 该实际源地址`（含 IP）。这样断言才真正闭环。

### B.3 断言 22 的专项判定（委托 B.3）

**问题：脚本自己算的 sha256 与被测程序算的 sha256 是否来自同一条代码路径？如果两者都是脚本算的，那它证明的是什么？**

**答：不是同一条代码路径，而是两条真正独立的实现。这是本实验最有价值的设计。**

证据链：

- 脚本侧 `:254-258 function Get-Sha256Hex` 使用 .NET 的 `[System.Security.Cryptography.SHA256]::Create()`——**Windows CNG / BCrypt 的成熟实现**。
- Agent 侧 `main.rs:97 fn sha256_hex(data: &[u8]) -> String` 是**零依赖手写 SHA-256**（64 个 K 常量、8 个 h 初值、标准 padding、`rotate_right` 消息调度），且在 `main.rs` 的单元测试（本报告 §2 快照中的 `sha256_matches_known_vectors` 附近）用 `b""`、`b"abc"`、64 字节等已知向量自测过。
- 因此断言 22 是 **.NET 实现 vs Rust 手写实现**的交叉验证。若手写 SHA-256 有任何一位错，10 个哈希会全错，断言必然失败——**这是真实有效的强断言**。

**它证明的是什么（精确表述）**：

1. 脚本构造的 8 字节载荷（`17320000FFFF` + 后缀）与
2. Agent 在**转发前**记录的哈希（`forward-log` 的 `sha256=`）与
3. Agent 在**转发后从对端 socket 收到**时记录的哈希（`peer-recv` 的 `sha256=`）

三者逐帧全等。即：**载荷在"脚本构造 → Agent 入站解码 → 转发 socket 出站 → 对端 socket 入站"这条链上没有发生任何字节级改动**，且两个独立的 SHA-256 实现互证。

**但要注意两点（这是需要写进文档的边界）**：

- 三方中的 (2) 与 (3) **由同一个进程、同一个 `sha256_hex` 函数计算**。它们互证的是"数据没变"，不是"两个独立观察者"。真正的独立观察者只有脚本一侧。
- `peer-recv` 行的哈希是按行内 `sha256=$want\b` 匹配的，**不校验该行对应哪个 `n=` / `from=`**。若同一个哈希在 10 行里出现两次（例如重传同一载荷），`$peerLine.Count -eq 1` 会使断言失败——这实际上是**对重传有一点点间接鉴别力**，是脚本里少见的自我保护。这一点文档没有提到，值得补上。

**结论**：断言 22 **成立且强**，文档 §3 第 22 行"sha256 + 全字节三方对账 / 10/10"的措辞**准确**。本审计独立复算 10/10 全等（§A.3），可以确认这条不是纸面通过。

### B.4 断言 17 的专项判定（委托 B.4）

**问题：`forwarded == peer received` 在原理上能不能证明"不重传"？如果程序重传了但接收端丢弃了重复包，等式是否还成立？接收端这里有没有去重逻辑？**

**答：在原理上不能；只有在"接收端不去重"这一附加前提下才能部分成立；本实验的接收端确实没有去重。**

分四层说：

**第一层：接收端有没有去重？** 没有。`main.rs:834 fn drain(&mut self, buf: &mut [u8], ...)` 的循环体只做三件事：`received += 1`、`bytes += len`、更新 `first_from`/`last_from`，然后写一行日志。**没有哈希比对、没有 seq 跟踪、没有"这个包我刚见过"的判断。** 这是对实验有利的事实。

**第二层：如果重传了——哪怕接收端不去重——等式还成立吗？** 一般情形下不成立：发 10 个 + 重传 k 次 → `received = 10 + k ≠ 10`，等式失败。所以本实验的等式**确实排除了"在无去重接收端上发生的重传"**。

**第三层：但这种排除是有条件的，条件却没被验证。** 存在一类组合可以让等式在"有重传"时仍然成立：**重传发生 + OS 恰好丢掉等量的包**。具体地，如果 Agent 重传了 k 个包，而 UDP 接收缓冲区同时溢出丢掉 k 个，`received` 仍可能正好是 10。在环回 + 8 字节 + 0.5 s 间隔这个场景下，这几乎不可能发生（环回不丢包、缓冲区远大于 80 字节），但**实验没有测量丢包，所以"几乎不可能"是推理而非证据**。要彻底封堵这个洞，需要负向对照（见 §F.2）。

**第四层：最根本的问题——运行期等式本来就不是"不重传"的正确证据。** "不重传"是一个**代码路径属性**，它的正确证据是代码评审：`main.rs:757` `match self.sock.send_to(&frame.payload, self.target)` —— 每个进入 `consider` 的被接受帧，**只有这一次 `send_to` 调用**；`Ok(n) if n == frame.payload.len()` 分支只做 `forwarded += 1; bytes += n`，没有任何重试、补偿、定时器、队列重放。没有 `loop`、没有 `retry`、没有 `for` 包着 `send_to`。`_ =>` 失败分支也只是 `forward_fail += 1`，**不重发**。

所以：**"不重传"是真的，但它的证明在代码里，不在 `forwarded == peer received` 里。** 文档 §5 第二条（`:95`）"转发是**一帧一次**：`forwarded == peer received == 10`，没有出现应用层重传或补发"把结论挂在了一个只能算旁证的等式上。这是**表述越界**（F3C-R-04），需要改成"代码路径保证单次 `send_to`（引用 `main.rs:757`）；运行期 `forwarded == peer received == 10` 与该性质一致，且因接收端无去重而具备一定的旁证价值"。

**另外**：断言 15（`duplicates=0`）只统计**入向**重复。转发出去之后若发生重复，`PeerStats` 里没有任何计数器能发现——它只数"收到几个包"。所以"无重复"这个结论在**出向**方向上是空的。文档 §5 第一条（`:94`）"`seq` 连续、无重复、无重排"容易被读成整条链路的性质，实际只覆盖 Agent 入站。

  2. 因此 F3-C **不能**用来声明"20B 探针在真实场景下的行为"。文档 §5 已把 datapath 回包列入"不证明"，方向是对的，但没有点出 src 差异这个具体机制。

### C.2 §5.2 回包策略：`reply sent: 1` 与"对端全程不回包"是否冲突（委托 C.2）

**答：不冲突，但文档的表述需要更精确地区分两个"回包"概念，而且这个 20B 探针目前没有任何断言覆盖。**

先把三个事实摆清楚：

1. **设计 v0.3 §5.2（`docs\F3-DIRECT-RELAY-DESIGN-20261114.md:100`）** 要求"合法策略二选一并在每项测试注明：D4 兼容（每运行 ≤1 个 20B 固定探测）**或** 不回包（F3-C 退避语义恰以不回包实现）"。
2. **本次运行的 `summary.txt:24`** 是 `reply sent : 1 (D4: at most ONE 20B local probe per run)`，`:25` 是 `reply skipped : no_endpoint=0 not_local=0 already_sent=9`。即 Agent 的 **datapath 侧**确实发了 **1 个 20 字节**的本地探针，发往 `127.0.0.1:21345`（脚本的发送端口），源端口 55017（`datapath-log.txt:3`：`datapath reply sent 20B to 127.0.0.1:21345 (ephemeral src port 55017) - local probe only`）。
3. **转发目标 `127.0.0.1:21347` 全程没有回包**——`summary.txt` 里没有任何"peer 发出"的计数器，`forward-log.txt` 的 `peer-recv` 行都是"对端收到"，不是"对端发出"。

所以两个"回包"是**不同 socket、不同方向、不同目的端口**：

| 概念 | 谁发的 | 发给谁 | 次数 | 是"对端回包"吗 |
|---|---|---|---:|---|
| datapath D4 探针 | Agent 的 datapath 侧（`reply_sock`，源端口 55017） | 帧的**发送方** `127.0.0.1:21345` | 1 | **否**。它是 Agent 反向给发送方的一次探测，不是对端（21347 监听器）发出的 |
| 对端回包 | 不存在 | — | 0 | — |

**判定**：

- **不冲突。** "对端全程不回包"指的是监听 21347 的转发目标从不主动发数据；这与"Agent 的 datapath 侧发了 1 个 20B 探针"是两件正交的事。文档 §2.5（`:34-35`）已经明确写了这个区分："D4 探针由 Agent 的 datapath 侧发往 62056 场景的**发送方**，与这里的转发目标无关"。**这段表述是准确的，应予以肯定。**
- **但有两处需要补强**：
  1. **设计 §5.2 说"二选一"**，而 F3-C 实际上**同时**采用了"不回包"（转发链路）与"D4 兼容"（datapath 链路）。文档应从"策略二选一"的角度说明：**转发链路上选"不回包"；datapath 链路上因 `--simulate-datapath` 的存在而必然产生 1 次 D4 探针，这是 Agent 既有行为，不是本实验选择的策略。** 当前文档 §2.5 只说"这是 §5.2 的策略边界"，没有说清"本实验在两条链路上分别处于哪一档"。
  2. **`reply sent: 1` 没有任何断言覆盖。** 脚本的 12 个 `Grab` 里没有 `reply sent` 一项，23 条 `Check` 里也没有一条断言 `reply sent == 1` 或 `already_sent == 9`。也就是说：**文档 §3 表格里根本没有提到这个 20B 探针，它只在 §5.2 的讨论里出现过。**如果 Agent 的 D4 上限逻辑坏了（比如发了 10 次），本次测试**不会红**。这是一个真实缺口（F3C-R-11），修法很简单：加两条断言 `reply sent -eq '1'` 与 `already_sent -eq '9'`，正好把"D4 最多一次"这个设计约束纳入回归。

- **另一个值得记录的细节**：这个 20B 探针被发到了 `127.0.0.1:21345`，也就是**脚本自己的 `UdpClient` 端口**。脚本从不从 `$sender` 读数据（它只 `Send`），所以这个探针**一直躺在脚本 socket 的接收缓冲区里，从未被读取**。它不影响任何断言，但说明"Agent 发了探针"这件事在脚本侧没有闭环验证——只有 Agent 自己的 `reply_sent` 计数器能证明它发了。

### C.3 `mappings created == 1` 是否验证了"键复用"（委托 C.3）

**答：部分验证，但不足以支撑"键复用"这一结论，本质上是弱断言。**

先看设计 v0.3 §3.2（`:56`）：出向键是 `(session_id, logical_socket_id, socket_generation, dst)`，四元组（代码里实际是五元组，含 `dst_ip` 与 `dst_port`，见 `main.rs:669-675` 的 `ForwardMapKey`）。

再看夹具：10 帧全部是 `session=1`、`sock=2`、`gen=1`、`dst=127.0.0.1:62056`——**只有一种键**。

于是 `mappings created == 1` 能证明什么、不能证明什么：

**能证明的**：
- 实现**不是**"每帧建一个键"（那样会是 10）。这是一个真实的负向排除，`main.rs:702 fn ensure_mapping` 的 `keys.iter().any(...)` 线性查重确实起作用了。**这一点不空洞。**

**不能证明的**：
1. **不能区分"按四元组正确分键"与"只用一个全局键"。** 一个把所有帧都映射到同一个键的（错误）实现，同样会得到 `mappings created == 1`。要区分，需要**至少第二种键**：例如再发 1 帧 `gen=2`（或 `sock=3`、或 `dst` 换成另一个端口），断言 `mappings created == 2`。**当前夹具做不到。**
2. **不能证明"键的正确性"，只能证明"键的计数"。** 即使 `ensure_mapping` 用了错误的字段组合（比如漏掉 `socket_generation`），在单键夹具下仍会返回 1。**要证明字段组合正确，必须构造"某字段不同 → 应新建键"与"某字段相同 → 应复用键"两组对照。**
3. **不能证明表满行为。** `MAX_FORWARD_KEYS = 64` 从未接近。
4. **文档措辞过强。** §3 第 9 行写"（同一键在 10 次重试中复用）"——描述是准确的；但 §5 第三条（`:97-98`）写"10 次重试复用**同一个映射键**（`mappings created == 1`），说明发现期/重试期的会话表不会被同一次加入反复扩充"——这个推论在单键夹具下是**同义反复**：只有一个键，当然不会被反复扩充。真正要证明的"会话表不会被反复扩充"需要"多个键共存时，重复的键不新增"的对照。

**修法**：在夹具里加 2 帧（不破坏 10 帧退避主线，可放在主序列之后）：
- 1 帧 `gen=2`（其余不变）→ 期望 `mappings created == 2`；
- 1 帧与第 1 帧完全相同 → 期望 `mappings created` 仍为 2。

这两帧能把 `mappings created` 从"计数巧合"升级为"分键语义验证"，成本极低（不改变主实验时长，可放在 128 s 之后或另起一次短运行）。

### C.4 其他一致性问题

- **文档 §5 第 4 条 `:104` 的"618 字节的 CVLH2 封装"与代码不符**（F3C-R-12）。代码 `main.rs:45 const FRAME_HDR: usize = 42`、`:46 const MAX_PAYLOAD: usize = 1280`，8 字节载荷的 CVLH2 帧应为 **42 + 8 = 50 字节**。全仓库 grep "618"，除本文档这一处外，只命中哈希值与 mod ID 等无关文本，**没有 618 对应的任何常量或常量组合**。这是一个独立的数字错误，虽然只出现在"不证明"段落里（不影响主结论），但会削弱读者对文档其他数字的信任。
- **设计 §3.2 的 `no_mapping` 与实现的 `skip_key_table_full` 语义不一致**（F3C-R-13）。设计说"未命中则不转发并计数（`no_mapping`）"，实现里"未命中"的正常路径是 `ensure_mapping` **新建**键并返回 true，只有**表满**时才返回 false 并计 `skip_key_table_full`。也就是说实现里**不存在**"未命中即不转发"的语义——任何新键都会先被创建。`main.rs:1672` 的自我说明已经承认这是"PROTOTYPE LIMIT, not a design rule"。文档 §3 第 8 行的说明文字沿用了旧的"design v0.3 §3.2 step 2"表述，会误导读者以为这个上限是设计要求。**证据 `summary.txt:38` 的文案正是这段旧文案，而当前源码已经改成自述"PROTOTYPE LIMIT"——这再次印证 §A.1 的"二进制已改、证据未重跑"。**

## D. 表述边界

### D.1 §5 四条"证明"是否有对应证据

文档 §5（`:92-99`）列出 5 个要点（其中前四条是"证明"，第五条也是"证明"）。逐条判定：

| 文档"证明" | 对应证据 | 本审计判定 |
|---|---|---|
| ①（`:94`）10 帧退避序列逐帧穿过转发链路，`seq` 连续、无重复、无重排 | `frame-log` 10 帧、`forward-log` 10 对、`summary:13` 计数全 0 | **成立，但范围仅入向**。`seq` 连续/无重复/无重排由 `note_seq` 在 **Agent 收包侧**统计；转发后到对端的重复**没有计数器**。措辞应加"（Agent 入站侧）" |
| ②（`:95`）转发是一帧一次，`forwarded == peer received == 10`，没有应用层重传或补发 | `summary:34` `forwarded: 10`、`:43` `payloads recv: 10` | **等式成立，结论越界**。真正的证据是 `main.rs:757` 单次 `send_to`；见 B.4 / F3C-R-04 |
| ③（`:96`）8 字节载荷在三处 sha256 完全一致 | `forward-log` / `peer-recv` 各 10 个 sha256，本审计独立复算 10/10 | **完全成立，本轮最强**。无需修改 |
| ④（`:97-98`）10 次重试复用同一个映射键，说明会话表不会被同一次加入反复扩充 | `summary:39` `mappings created: 1` | **前半成立，后半是同义反复**。单键夹具下"不会被反复扩充"必然成立；见 C.3 / F3C-R-05 |
| ⑤（`:99`）Agent 全程未占用 62056，且对端收到的来源就是本进程的转发 socket | `bind-check.txt`、`summary:32/45` | **前半弱、后半未成立**。①"未占用"无法区分"无人占用"且仅瞬时采样；②"本进程的转发 socket"未经 PID 验证，只比了端口数字；见 B.1 / B.2 / F3C-R-03 / F3C-R-09 |

**结论**：5 条"证明"中，**仅第 ③ 条完全站得住**；①④ 需要限定范围，②⑤ 需要重写。

### D.2 "不证明"清单是否完整

文档 §5（`:101-110`）列了 6 条：真实双机/跨网/NAT/Relay、游戏侧行为、退避序列来源语义与放弃点、时延与 0.5 s 首窗、长稳、并发。**方向都对，但不完整。** 建议补充以下 6 条：

1. **不证明"重传检测能力"存在**——本实验没有任何负向对照，无法区分"因为没重传所以等式成立"与"重传了但计数器看不见"。**这是最重要的一条缺口**（F3C-R-06）。
2. **不证明出向去重/重复可见性**——`PeerStats` 只数到达，不跟踪 seq；转发链路上的重复不可观测。
3. **不证明 `62056` 被真实游戏占用时的行为**——本实验里 62056 空闲（`bind-check.txt` 看不出占用者），而真实场景下游戏会绑定它。H2 门槛的核心冲突场景**没有被构造**。
4. **不证明载荷长度 ≠ 8 的行为**——全部 8 字节；`MAX_PAYLOAD = 1280` 的上界、多帧拼接、`hex4` 只打印前 8 字节但 sha256 全长的组合均未测试。
5. **不证明 `flags` 其他取值的行为**——全部 `0x21`；`FLAG_REJECTED_OVERSIZE` / `FLAG_NO_PAYLOAD` 的拒绝路径、`rejected` 计数、`skip_discovery` 分支均未触发。
6. **不证明映射表容量与淘汰**——`MAX_FORWARD_KEYS = 64` 从未接近，设计里也没有淘汰策略。

另外，第 5 条（`:109`）"不证明长稳：单次运行 257.9 秒"写得偏保守地准确，但可以更明确：**真正缺的是"在 128 s 级别的空闲间隔后 socket 仍存活"这类长寿验证**——本实验恰好覆盖了 128 s 那次，这是加分项，可以写进"证明"而非只列在"不证明"里。

### D.3 是否存在把回环结果暗示为联机/跨网/游戏侧验证的措辞

**总体上没有越界，纪律性好于预期。** 具体核查：

- 文档 `:3-4` 开篇即写"本文只描述本机回环原型，不构成任何联机验证，也不移动 Gate A/B"。**这句是清楚的。**
- `summary.txt:28` 的 `mode : LOOPBACK SELF-TEST (--loopback-selftest) - NOT a real-machine result` 与 notes 段的 `LOOPBACK PROTOTYPE` 是程序自带免责声明。**好。**
- `forward-log.txt` 首行注释 `# civlink-agent 0.3.0 - F3-A forward prototype (loopback only, verbatim payload, no retransmit)` 也标了 loopback。**好。**

**但仍有 3 处措辞偏强，建议收窄**：

1. **文档标题与文件名**：`F3C-BACKOFF-20261114.md`、§1 "退避语义实验"。标题不带"回环原型"，只有正文第一句带。若被上游摘要引用（例如 `CODEX-HANDOVER-M0A.md` 的编号清单），容易丢掉限定词。**建议文件名或副标题加 `-LOOPBACK`。**

### E.4 最小补强实验（如果只做一件事）

**做这一件：在现有脚本末尾追加 3 帧负向对照（约 +30 秒，不改变主实验）。**

具体设计：

```
主序列 10 帧跑完（128 s 之后）追加：
  F11: seq=10（重复上一帧的 seq，载荷用 35BA）   -> 期望 duplicates == 1（若 note_seq 正常）
  F12: seq=12（跳过 11）                          -> 期望 seq gaps == 1
  F13: 与 F01 完全相同（session/sock/gen/dst/载荷全同） -> 期望 mappings created 仍为 1（验证复用）
同时新增两条断言：
  Check 'duplicate seq is observable'  ($dups -eq '1')
  Check 'seq gap is observable'        ($gaps -eq '1')
```

**为什么这一条能补上最大的洞**：如果 `duplicates` 与 `seq gaps` 能被这三帧点亮，就证明"计数器是活的"，那么主序列里 3 个 `0` 才有意义（否则无法区分"真的没有"与"计数器坏了"）。这是**负向对照**的最小形态，成本极低，收益最大。

**如果只做第二件事**：加 `reply sent -eq '1'` 与 `already_sent -eq '9'` 两条断言（F3C-R-11），把设计 §5.2 的 D4 硬约束纳入回归。
