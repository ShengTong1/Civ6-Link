## 1. 结论摘要

**不建议当前工具包进入正式 CivLink M0-A 实验，也不批准 Gate A。** REV-001 的“P0 十项已完成”多数在源码层有对应实现，但仍有未解决的关闭路径缺陷及验证证据边界问题；此外，追踪器记录并不等于 Civ6 行为审计。README v1.1 明确称 2026-11-10 的本机验证完成 31/31 Hook，但随附 REV-001 运行证据只显示合成 PowerShell UDP 场景，不能证明 Civ6 Steam/EOS 环境下观察完整性或无扰动性。

## 2. 问题清单

### P1-1：重复调用 shutdown 后无法继续卸载，可能永久留下已停用 DLL

**源码确认。** `CivLink-M0A-audit/civtrace/trace_dll.cpp` `CivTraceShutdown()` 第 1342–1352 行：第二次调用只返回 `1`；首次返回 `0` 后会完成关日志等操作。注入器 `CivLink-M0A-audit/civtrace/injector.cpp` `main()` 第 301–318 行接受 `0/1`，但 FreeLibrary 循环条件是 `i < 2 && sc == 0`（311 行）。若第一次 Shutdown 已成功但 FreeLibrary 失败/超时，或进程中存在已 shutdown 的模块，重试会得到 `sc==1`，跳过 FreeLibrary，最终仍报告模块残留并退出 2。该状态不可由注入器重试恢复。

**技术理由：** 幂等 shutdown 与卸载动作被错误绑定到“本次调用返回 0”。返回 1 已明确表示此前完成 shutdown，应该同样允许执行已确认安全的卸载步骤；需同时审查引用计数和逐次 FreeLibrary 结果，不能盲目调用两次。

**测试确认：** REV-001 `run2-T3-shutdown-unload.txt` 只验证首轮 code=0 的路径；未见 code=1 后继续卸载或 FreeLibrary 失败后的恢复测试。

### P1-2：关闭跟踪 DLL 时未确认 Hooks 已禁用，等待刷盘不能代替在途 Hook 排空

**源码确认。** `trace_dll.cpp` `CivTraceShutdown()` 第 1347–1351 行在 `MH_DisableHook` 失败时只设置 `ok=false`，仍 join flusher、调用 `MH_Uninitialize()` 并 DrainAndClose；`InitWorker()` 第 1334–1336 行在刷盘线程创建失败时仍继续安装 Hooks。注入器虽然对 Shutdown 返回 2 拒绝 FreeLibrary，但 `DllMain` 的非进程退出兜底第 1368–1378 行仍在禁用失败时 join/detach 后执行 `DrainAndClose()`。日志队列锁只保护 Emit/队列，不能证明所有 Hook 执行体已退出。

**技术理由：** 必须证明 Hook 入口已关闭且在途调用已排空，才能关闭日志资源或卸载代码。当前实现把刷盘线程生命周期与 Hook 执行体生命周期混为一谈；注释所称“join 刷盘线程等待 Hook 退出”并无代码依据。该风险在 MH_DisableHook/MH_Uninitialize 失败路径尤其突出。

**测试确认：** 报告称正常目标线程/句柄无泄漏，但没有构造 MinHook 禁用失败、安装中 Shutdown 竞争、FlushLoop 创建失败的场景。

### P1-3：启动刷盘线程失败时仍启用全部 Hooks，可能导致长时间无日志和强杀丢证

**源码确认。** `trace_dll.cpp` `InitWorker()` 第 1334–1336 行捕获线程创建失败后只 Emit 提示，随后无条件 `InstallHooks()`。此时日志只会在最终收尾时刷出；被强杀时会丢失全部未落盘队列，与 README 对“独立刷盘线程、强杀保留已刷盘日志”的保障不符。

**技术理由：** 对取证工具而言，刷盘线程失败应阻止启用 Hooks，或切换到已明确验证的安全降级行为；仅将错误放入同一队列无法保证错误提示本身落盘。

**测试确认：** `run2-T1` 实时增长验证了成功创建线程的路径；线程创建失败和强杀组合未测。

### P1-4：进程枚举上限会静默漏掉目标，可能选择错误 PID

**源码确认。** `injector.cpp` `FindPids()` 第 62–73 行固定接收容量；主程序第 213–229 行仅保存 32 个匹配项，超过容量仍继续枚举但不报告截断，然后可能把第一个 PID 当目标。README §2 声称列出“全部匹配 PID + 完整镜像路径”。`PrintExePath()` 第 76–82 行在无法打开进程或读取路径时静默返回。

**技术理由：** 运行多个同名进程/受限进程时，操作对象选择不完整且路径确认不完整，与实验的目标 PID 消歧要求冲突。应动态扩容或明确拒绝截断；路径不可用必须报告。

**测试确认：** REV-001 T1–T6 没有多于 32 个目标进程或路径不可访问案例。

### P1-5：WOW64 检测失败被当成“不是 32 位”继续操作

**源码确认。** `injector.cpp` `main()` 约第 249–260 行（需以源码行定位核验）调用 `IsWow64Process(h, &wow64)`，只有 API 成功且 wow64 为真才拒绝；API 失败时继续注入/卸载。该工具按 REV-001 声明只支持 x64 DLL。

**技术理由：** 架构未知不能安全地解释为 x64。应使用 `IsWow64Process2` 或对查询失败 fail closed，并把错误原因写入诊断。远程线程入口和 DLL 位数不匹配可能造成加载失败或不可预测状态。

**测试确认：** REV-001 报告明确 32 位目标拒绝分支未构造。

### P2-1：模块枚举固定 1024 项，缓冲不足可能把“未找到”误报为“未加载”

**源码确认。** `injector.cpp` `QueryRemoteModule()` 第 92–111 行固定 `HMODULE mods[1024]`，`needed` 超过缓冲容量后把 `count` 截到 1024 并照常返回 0（未找到）。调用端把 0 当作确定未加载（卸载分支第 261–266 行；注入分支约第 361 行）。

**技术理由：** PSAPI 的 `needed` 可用于发现缓冲不足；截断时必须扩容/重试或返回“不可判定”，不能把枚举不完整等价于不存在。模块极多虽非典型 Civ6 环境，属于安全判定错误。

### P2-2：`IsWow64Process` 的系统调用失败未检查，且权限特权启用状态未验证

**源码确认。** `injector.cpp` `EnableDebugPrivilege()` 第 48–59 行忽略 OpenProcessToken、LookupPrivilegeValue、AdjustTokenPrivileges 的失败和 `ERROR_NOT_ALL_ASSIGNED`；主流程仅检查 `OpenProcess` 后报通用管理员提示。叠加 P1-5，架构和权限状态不可观测。

**技术理由：** 审计工具必须把前置条件失败与“目标架构不匹配/被 Defender 拦截”区分，避免操作员误判原因。此项不代表每次注入必然失败。

### P2-3：日志队列有界，但每条 Hook 仍同步分配、格式化并获取多把锁

**源码确认。** `trace_dll.cpp` `Emit()` 第 227–243 行在 Hook 调用线程同步执行 QPC/墙钟读取、`snprintf`、`std::string` 分配，并持有 `g_mu`；caller/socket 状态路径还会使用其它 mutex（例如 `CallerOf()` 第 367 行起，socket 状态维护第 427 行起）。这不是“同步写磁盘”，但不等于线程无阻塞。

**推断/风险。** README 把“日志不阻塞游戏线程”概括得过强。Mutex 争用、堆分配和系统调用可能增加 Hook 延迟，改变 H6 短窗口/时序；现有注入对照方案能估计影响，但尚无 Civ6 实测。建议文案改为“无同步磁盘 I/O；日志路径仍有锁与分配开销”，并将注入/原生对照列为结果解释约束。

## 3. REV-001 P0/P1 复核

- **P0-2 卸载契约：源码部分确认。** `injector.cpp` 第 275–308 行先校验身份并要求 Shutdown 返回 0/1 才进入卸载，满足“不确认不 FreeLibrary”；但 P1-1 的重试缺陷及第 310–318 行无条件最多两次 FreeLibrary，意味着报告中“引用计数=1/重复注入时=2”的假设并非通用契约。每次远程调用没有读取 FreeLibrary 线程退出码，调用失败/超时后仍可能继续下一轮，需修正。
- **P0-3 远程模块发现：主要路径确认，但容量边界不安全。** PSAPI 取全精度基址/尺寸属正确方向；P2-1 会将不完整枚举变成“未加载”。
- **P0-4 PE 地址解析：部分确认。** 本地导出 RVA 与远程头身份检查存在；`RemotePeIdentity()` 第 151 行在 `sizeOfImage==0` 时直接返回 true，虽通常被前置解析约束挡住，但属于 fail-open 辅助函数语义；`GetExitCodeThread()` 返回值未检查（176–188 行），取码失败时默认 code=0，存在把未知状态误当成功的风险，应检查 API 返回值。
- **P0-5 并发安全：未能确认完整。** 正常 shutdown 顺序有显式线程 join，但没有独立在途 Hook 计数/屏障；见 P1-2。`g_shutdown` 在调用线程加入初始化线程前被置位，`InitWorker` 没有在安装 Hooks 前检查 shutdown，存在并发关闭与装钩交错的可能（第 1334–1349 行）。
- **P0-6 Overlapped 三态：源码可见但未经针对性测试。** Hook 条目采用完成态条件读取；报告已披露 GQCS 路径未覆盖。
- **P0-7 ErrTx：实现意图合理，未有错误槽位定向断言。** `ErrTx::end()` 第 202–206 行按 win32/WSA 路径恢复；REV-001 真实 UDP 日志并不能证明调用方随后读到的 last-error 与原 API 完全一致。
- **P0-8/9 队列与 drop 统计：源码确认基本路径。** 队满丢弃计数、收尾汇总可见（232–235、DrainAndClose）；drops>0 未被运行触发。锁本身仍可能阻塞 Hook，见 P2-3。
- **P0-10 31 API：数量和表项可读，ABI 与行为未做独立逐项外部核验。** 31 项安装记录只能证明目标合成进程内安装结果；未证明 Civ6 所有路径均经过这些导出，也不覆盖静态导入/手动解析/其它扩展函数。
- **P1 手册/实验流程：** 手册要求 E2-B 以 B 端 `closesocket` 计算生命周期，但其表述与 H6 结论仍依赖客户端 socket 是否由同一 socket 发起/接收响应；应该同时以抓包和日志关联 socket/端口，并明示追踪丢行时不可计算。E4 方向矩阵是合理的三端取证要求，但“逐台 Conversations”仍需过滤已确认游戏 PID/端口，否则其它 UDP 流量可污染矩阵。

## 4. 证据等级与边界

### 源码确认

以上标注“源码确认”的事项来自当前工作区源码静态阅读，路径和函数/行号可复查。它们不代表运行时已触发。

### 测试确认

REV-001 随附 `docs/reports/rev001/run2-T1...T6.txt`、`run2-log-*.log`、SHA256 文件和 `build-rev001.log` 记载了 MSVC 构建、合成 UDP 注入、重复注入、正常卸载、错误 DLL 拒绝、未注入卸载与强杀。报告内的数值与日志增长可作为“提交的测试证据”引用。本审计没有重新运行这些测试，也没有从现有工作区重新构建二进制并复算报告 SHA256。

### 推断

性能扰动、锁竞争对窗口的影响、游戏对 API 覆盖之外路径的使用情况、极端进程/模块数情形均是基于源码机制的风险推断，尚未在 Civ6 环境中复现。

### 未验证

- Civ6 Steam/EOS 真实进程的 E1–E5；README §1 的“本机验证 31/31”不是协议行为证据。
- E2-A/B 的发现响应及 H6 时窗；E3 的 H3 五分类；E4 三台设备的 H7 拓扑和 H11 对照；E5 EOS。
- REV-001 披露的 SizeOfImage 不匹配、远程 PE 头不匹配、32 位目标、IOCP 限流、drops>0 分支。
- `GetExitCodeThread` 失败、FreeLibrary 失败/超时、重复 Shutdown、DisableHook 失败、线程创建失败、安装/关闭竞态、容量截断。
- 注入与原生对照的时序一致性、日志 drop 对 H6 统计的影响。

## 5. Gate A 判断

**当前不满足 Gate A。** 规范 §11 要求 M0-A 实验和协议行为报告完成，并裁决 H3/H4/H6/H7/H8/H9/H10/H11。现有材料只有审计工具包和合成负载 REV-001 测试；README 也明确 E1–E5 尚未执行。先处理本报告的 P1 项、补齐可复现的工具级测试证据，再按 README 执行真实实验，之后才可评估 Gate A。
