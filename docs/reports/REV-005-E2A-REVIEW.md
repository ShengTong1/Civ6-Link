# REV-005 E2-A 双机广播发现独立复核

- 日期：2026-11-12（Asia/Shanghai）
- 被审材料：`docs/reports/REV-005-E2A-SUBMISSION.md`、`docs/reports/M0-A-协议行为报告-E2A-20261112.md`、PC-A/PC-B 原始证据目录
- 结论：**原始证据完整性与若干数据面观察通过有限采信；C-3 的因果/唯一性结论不通过。当前材料不足以验收完整 E2-A（房间响应/H4 未完成且注入状态记录矛盾）。不批准 Gate A，不启动 M0-B。**

## 1. 证据完整性与独立复算

### 已直接确认

1. 提交报告 REV-005 的 SHA256 与提交值一致：`BE4F67A0558B875C61ECB5C788471D04F38A1C5EF658B7EAA2C95C607494E195`。
2. E2-A 报告 SHA256 与提交所列完整值一致：`289F608067A46BDDE6C1FACA4F1388D11B421CD78575C9559DD497C57FF6A68F`。
3. PC-B 的 `SHA256SUMS.txt` 共 24 项，复算 **0 mismatch、0 missing**。PC-B 17:09 pcapng SHA256 为 `5E2369481FA129952B465E0105290A7A6ED504FE592DA6C336C74C21C39735E8`；PC-A 17:47 pcapng SHA256 为 `E746BF780B5B992FD559645D60EABCD1B5211A0B324E605281BA3E3D306D638E`。
4. 对两份 pcapng 用已入仓 `M0A/pcb-kit/analyze-pcapng-datagrams.ps1` 重新解析：PC-B 文件匹配 6,400 条记录、归并为 800 个数据报身份，均为源 `26.187.101.177`；PC-A 文件匹配 5 条捕获记录，归并为一个身份。当前解析器的逐副本帧哈希检查通过。
5. PC-A 唯一身份与 PC-B `lanprobe-round3-refresh.log` 的同一包在源 IP、源 UDP 端口 53787、目的端口 62900、载荷 `8d e8 fc 70` 上一致。PC-A 侧记录 5 个捕获副本、IP ID 12255、帧哈希一致。**这强力支持两个端点观察到同一广播数据报**，但三个字段“无法巧合”属修辞；应以 tuple/载荷/帧本身一致作证，不声称概率为零。
6. PC-B `lanprobe-round3-refresh.log` 统计 500 条本地接收记录：499 条源地址为 PC-B Radmin、1 条源地址为 PC-B WLAN。PC-B 两份 pcapng/CSV 与 LAN probe 属不同观测层，但 LAN probe 没有 PID 字段，进程归属是按游戏操作窗口和报文特征判断。
7. PC-B `lanprobe-g2-window2-final.log` 有 496 条源 IP `192.168.31.59`（PC-A WLAN）的记录，接口为 WLAN；这支持本次配置下 PC-A WLAN 广播到达 PC-B WLAN。此项只证明被观测广播可达，不证明游戏房间发现/加入完成。

## 2. 结论逐项裁定

### C-1：发现报文大部分使用 Radmin 源——有限通过

PC-B pcapng 在 17:09 的 60 秒窗口中有 800 个发现签名数据报身份，均呈现 Radmin 源 IP/MAC。后续 `lanprobe` 五次刷新记录中为 499/500 Radmin、1/500 WLAN。可以写成：

> 在本次 PC-B 配置与采集窗口内，匹配发现签名的报文大部分呈现 Radmin 源地址；五次刷新接收记录为 499/500 Radmin、1/500 WLAN，另一个 17:09 pcapng 窗口的 800 个身份均为 Radmin 源。

不要把跨不同窗口的 800 + 500 合并成一个统一分母，也不要把 LAN probe 的 socket 接收记录称为独立的进程级来源证明。

### C-2：WLAN 两方向有广播可达证据——有限通过

- PC-B→PC-A：一个 WLAN 源广播数据报被 PC-A pcapng 观察到，tuple 与 PC-B lanprobe 相符。
- PC-A→PC-B：PC-B lanprobe 观察到 496 个 PC-A WLAN 源数据报。

据此可采信“本次拓扑和采集窗口中，两方向均观察到至少一个 WLAN 源广播到达对端”。不能扩大为“WLAN 链路完全正常”“Civilization VI 已完成发现”，也没有完成加入或数据面测试。

### C-3：InterfaceMetric 是唯一原因/唯一障碍——不通过

**级别：P1，需撤回因果结论。**报告/README 将相关性写成已锁定根因，依据不足：

1. 报告称 `InterfaceMetric` 是“唯一决定因素/唯一障碍”（提交 §2 C-3、报告 §1/§4/§8；README v1.7 开头）。但本次未对 PC-B 做 metric 干预；REV-004 明确冻结了 apply/restore，PC-B 报告也确认未手工改动。没有控制变量实验，不能证明 metric 调整对游戏实际出口的因果效果，更不能证明“唯一”。
2. 同一 100 包刷新中，同一源端口 53787 的第一个包显示为 WLAN 源地址，后续 99 个显示为 Radmin 源地址。此现象本身证明出口并非“恒定由最小 metric 选择”，反而要求另行解释。报告将其归因于“ARP 邻居缓存为空→按最长前缀走 WLAN；缓存建立后→Radmin”（PC-B `PC-B-report-E2A.txt` §1/§4、提交 §2 C-3），**未有 ARP 缓存前后快照或受控实验支持**。
3. 目标是 IPv4 limited broadcast `255.255.255.255`，目标 MAC 为广播地址。当前证据没有展示需要针对此目标解析某个对端 MAC 的 ARP 过程；因此“ARP 缓存状态导致第 1 包先走 WLAN”的具体机制不能作为事实采信。应保留为未解释的源地址/接口变化，不要写作根因。
4. `netpath` 是路由查询/预测，不是实际数据包出口观测。真正的证据来自 pcapng 和本机接收记录；二者显示包行为，但不能单独证明其由 InterfaceMetric 唯一决定。
5. 实验还发现 PC-B 到 PC-A Radmin 地址的探测经普通网关/公网路径而非 Radmin 对端路径（报告 §5）。这说明该端点组合存在另一项 Radmin 可达性条件；更准确的表述是“本次两端没有验证出彼此的 Radmin 虚拟网络可达性”，不能把它折叠为单一 metric 障碍，也不能据此概括 Radmin VPN 整体不可用。

**允许的结论**：Radmin metric 较低与多数广播呈现 Radmin 源地址同时出现；WLAN 有少量/双向广播可达证据；目前怀疑是出口路由选择问题。**因果和首包机制未裁决。**

## 3. E2-A 实验条件与交付不一致

提交 §1、E2-A 报告 §0 称“A 注入、B 原生”；但 `A-side-evidence-final.md` 第 4、52 行明确记录关键 17:47 捕获“未注入本轮”，且证据目录没有对应 civtrace 原始 session log 或注入器运行记录。A-side 初版还记录握手未按协议发出且前两轮抓包窗口没有发现包。故本次确实获得了有价值的广播路由观察，但**不能把全部窗口笼统标注为标准的“A 注入、B 原生”E2-A**；需要逐窗口列 PID、是否注入、角色（host/client）、刷新时间和 capture 时间。

此外，E2-A 的被动发现/H4目标是确认房主响应及 1104B JSON。现有材料没有房主响应/JSON样本，PC-B 报告称房间显示受缓存影响，A 最后广播早于部分捕获窗口。故 **H4 与房主正向回复尚未完成，E2-A 的协议发现子项应标为部分完成**。

## 4. Radmin 路由与 metric 工具边界

- `tracert`、ping 与 ARP 记录可以支持“本次 PC-A/PC-B 的 Radmin 地址没有通过 Radmin 虚拟路径互达”，但不是普遍证明“Radmin 房间方案必须中继”；须先确认两端 Radmin network ID/成员状态/对端路由配置。
- metric helper 的 apply/restore 仍处 REV-004 暂停状态。**不批准在 PC-B 上运行 metric 修改，也不批准把 PC-A 当前变更称为恢复完成。**脚本修复应离线、单独复核，回滚需用保存的原始 Auto/Metric 状态并逐项验证。
- 产品“第 0 层 metric 修复”仍不采纳为已验收方案；当前只是候选 workaround。加入成功、副作用、不同拓扑兼容性均未验证。

## 5. 下一步决断

1. **先补一轮合规 E2-A 被动发现，不直接跳过**：两端记录进程/PID/角色/注入状态；A 明确保持建房/房间响应状态，B 原生刷新；按握手同步并双端同时抓包。目标是取得真实房主响应与原始 JSON/1104B 数据；若仍无响应，保留失败现场，按未验证报告。
2. **E2-B 不因“根因已锁定”而取消。**v2.1 §11.1 仍要求 H6 的 T_window/T_response 分布及 H9/H10 生命周期素材。E2-B 属 M0-A，需在合规 E2-A 归档后以全新进程、明确 tag/角色、双端抓包与日志对照执行；若注入改变行为，应报告差异，不把它当作污染而丢弃。
3. metric helper 可获准进行**离线脚本修复和代码审查**（防止覆盖原备份、保存所有被修改接口和 keep 接口原值、逐项 restore/readback、错误时非零退出）；这不授权在真实网卡上应用修改。
4. PC-A 的手工恢复：本次不执行。E0 与操作单对 WLAN metric 的记录存在 35/45 差异，且 Auto 状态没有完整原始快照。应先重建可信状态表，再由用户明确决定是否恢复；当前备份 `entries=[]` 不可作为恢复凭证。

## 6. Gate 状态

本次数据通过部分广播路径观察，不构成 Gate A 完成。E2-A/H4 需补正，E2-B/H6/H9/H10 仍未完成；H3/E3、E4/H7/H11（需第三台真实游戏端）、E5/EOS 等仍有缺口。**Gate A 不批准，M0-B 继续冻结。**
