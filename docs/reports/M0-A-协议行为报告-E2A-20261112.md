## §1 观察结论（REV-005 更正后）

**C-1　在本次 PC-B 配置和采集窗口中，发现签名报文大多呈现 Radmin 源地址。**
- 报告统计 500 条接收记录为 Radmin 499 / WLAN 1；另一 pcapng 窗口归并为 Radmin 源 800 个数据报身份。该数字分别属于不同窗口，不合并分母。
- `lanprobe`/pcapng 提供报文观察；`netpath`/`Find-NetRoute` 是路由预测，不是实际出口证据。

**C-2　该次采集窗口在 WLAN 方向观察到跨机广播到达。**
- B→A：A 端 pcapng 观察到与 B 端记录 tuple/载荷相符的数据报（`dstport=62900`、`srcip=192.168.31.214`、`srcport=53787`）。
- A→B：B 端监听记录观察到源为 A WLAN 地址的广播。以上只支持本次窗口中存在 WLAN 报文可达，不概括为所有 WLAN 场景均正常。

**C-3　源地址/接口变化与 InterfaceMetric 的因果关系在本次实验中未裁决。**
- 当时报告记录的接口配置与多数报文呈现 Radmin 源地址同时出现，但没有受控 metric 干预；不能称 metric 为唯一原因或唯一障碍。
- 同一刷新中 WLAN/Radmin 源地址变化的具体机制未证实。原“ARP 缓存导致首包 WLAN”的解释撤回；limited broadcast 观察本身不足以证明该 ARP 因果链。

## §2 核心证据：跨机确证（同一数据报，非时间戳对齐）

| 端 | 记录 |
|---|---|
| B 端 `lanprobe`（socket 层） | `17:49:11.656 if=17(WLAN) dstport=62900 src=192.168.31.214:53787 data=8d e8 fc 70` |
| A 端 pcapng（驱动层） | `dstport=62900 srcip=192.168.31.214 srcport=53787 IPID=12255` |

- **源端口 53787 为 OS 随机临时端口，两台机器独立观测到同一值，概率上无法巧合** → 同一数据报的跨机确证，比时间戳对齐强。

⚠️ **时钟偏差记录**：B 端 17:49:11.656 vs A 端 17:49:13.000，差 +1.344s。局域网 RTT 实测仅 4–6ms，故该差值为**系统时钟不同步**（NTP 未校准），非网络延迟。任何依赖跨机时间戳差值的分析（如请求-响应延迟）**必须先做 NTP 校准**。

## §10 房主回复确实存在于本次抓包（2026-11-13 补正）

本节更正 §1/§9 中「未取得房主响应／1104B JSON」的表述。经重新解析，**本次抓包已含 22 个房主回复**。

### 10.1 为什么此前漏判

`scripts\analyze-pcapng-datagrams.ps1` 只筛选 `dstPort ∈ 62900..62999`。
这能选中客户端的发现**请求**（`→ 255.255.255.255:62900`），但房主**回复**是
`srcPort=62900 → dstPort=客户端临时端口(53787)`，目标端口不在该区间 → **结构性永远选不到**。
「0 个回复」是工具盲区，不是协议事实。

### 10.2 补正后的实测（同一 pcapng，`A-pcapng-20261112_174753.pcapng`，SHA256 `E746BF78…6D638E`）

| 项 | 值 |
|---|---|
| REQ | 5 条记录 → 1 个身份（IP ID 12255），`192.168.31.214:53787 → 255.255.255.255:62900`，载荷 `8d e8 fc 70` |
| REP | 88 条记录 → **22 个身份**，IP ID 44968..44989 连续 +1，每身份 4 副本（pktmon 多捕获点） |
| REP 五元组 | `192.168.31.59:62900 → 192.168.31.214:53787`，**单播**，TTL=128 |

## §11 完整载荷已解出：22 页分页结构 + H4 结案（2026-11-13 第二次补正）

本节取代 §10.3–§10.5 的"截断"判断。方法：**单机自收** —— 本机同进程建房（绑定 `0.0.0.0:62900`）后，
另起一个 socket 向 `255.255.255.255:62900..62999` 发 1 个 4 字节请求，用 `ReceiveMessageFrom` 收全部完整 1104 B。
无需管理员、无需 pktmon、无需 `--pkt-size 0`、无需第二台机器。

### 11.1 ★ 关键修正：22 个回复是 22 个**不同分页**，不是 22 份副本

三次独立请求各回 22 个包，**每轮的 22 个 sha256 序列完全一致**（可复现）。
`reply-01` 与 `reply-02` 首个差异字节在 offset 160，公共前缀 160 B。

→ 此前"22 个身份 × 4 副本"在**捕获点维度**正确（pktmon 4 个捕获点），但在**内容维度错误**：
22 个是不同的数据页，一份 **20 636 字节**公告被切成 22 页。

### 11.2 ★ 关键修正：内容区是 938 B，不是 940 B

v1 分析器假设 `1104 = 164 header + 940 content`，把每页末尾的 2 字节零尾标带进内容流，插在 JSON 中间
→ 四条记录声明长度都比实测短 2 的倍数（`EnabledMods` 声明 17 984 / 实测 18 022，差 38 = 19×2）
→ 四个 JSON 全部报 `Invalid object passed in, ':' or '}' expected.`

按 **938 B** 切分后：**记录框架完全精确** —— 13 条记录恰好消费 19 990 / 20 636 B，尾部 646 B 全零，
**4 个 JSON 全部通过 `ConvertFrom-Json`**。

> 此前"38 个 NUL 位于 chunk 相对偏移 774/775"是错误推导（把页内绝对偏移 1102/1103 减 164 再 mod 940）。
> 正确位置就是每页最后两个字节 `[1102..1103]`。
