## 1. 验收依据

- 当前 `civtrace.dll` 与 `civinject.exe` SHA256 与更新报告 §2 和 `environment.txt` 相符。
- v0.4.4 注入器在 `CivTraceShutdown` 返回 0/1 后不执行远程 `FreeLibrary`；源码 `injector.cpp` §卸载分支明确打印 `intentionally LEFT MAPPED`。
- 成功关闭路径不调用 `MH_Uninitialize()`，MinHook trampoline 与 DLL 代码映射保留至目标进程退出；因此此前 B2 所担忧的“未能证明完全排空后，代码页/trampoline 被释放”被方案②消除。该判断仅适用于此审计运行模式，不构成生产热卸载安全证明。
- B1 超时分支在 5 秒后返回 2 并保留日志刷盘线程、MinHook 与队列；T14 提交输出显示首次超时拒绝关闭，阻塞解除后重试完成。
- T15 的 8 线程/6208 次调用样本中关闭成功；将其视为有限压力测试证据，而非数学上对所有调度交错的证明。方案②的安全性不依赖该压力测试覆盖所有竞态。
- C1 已更正。T1 显示关闭后模块仍在，重复注入识别为已加载，支持“保留映射”的操作契约。

本次是对已提交源代码与测试证据的审批复核；我没有重新构建，也没有重新运行 15 项测试。测试结论按提交的原始日志记录，不表述为审批员独立复现。

## 2. 强制操作限制

`-u` 在 v0.4.4 的实际含义是“停止 Hooks 并结束日志会话”，不是从进程卸载 DLL。关闭后，同一进程再次运行注入命令会被重复注入检查跳过，Hooks 不会自动重新启用。因此：

1. 每个需要重新开始追踪的实验阶段/重复轮次，必须先完全退出 CivilizationVI 进程，再重新启动并注入；不能仅靠 `-u` 后再次注入恢复追踪。
2. E2-A 到 E2-B、E4 各轮以及注入/原生对照之间，要按实验方案安排进程重启，并在记录中写明 PID、轮次、注入状态。
3. README v1.1 的“卸载”字样和流程需要在开始 Civ6 E1–E5 前更新为“停用 Hook、模块保留到进程退出”，并明确重启要求。若不更新，操作员会误以为同一进程可重复启停。
4. 外部工具或手工 `FreeLibrary` 仍可能触发 DllMain detach；本工具契约不保证抵抗外部强制卸载。M0-A 实验中不得另行对目标执行外部卸载。

## 3. 未解决但不阻断本审计模式的问题

- 入口并发下精确日志完整性仍未证明：一个未冻结的入口线程可能在排空计数检查后运行 detour。永久保留映射使其不构成已审范围内的代码页/trampoline use-after-free，但它可能在 `DrainAndClose()` 后追加事件或与日志收尾交错。因此关闭日志只能解释为“观察会话停止并尝试刷盘”，不能将 session-end 的序号解释为所有并发调用的绝对完整边界。M0-A 操作应在主菜单/静止阶段停用，并结合抓包与原生日志对照。
- 热卸载不受本次验收覆盖。若未来要在活动进程内释放 DLL 或 MinHook 资源，须另做同步设计与独立验收。
- T14/T15 和其余工具级测试的目标为合成进程；文明6 Steam/EOS 行为尚未验证。

## 4. Gate A 与后续阶段

本验收只确认 civtrace v0.4.4 可按上述限制进入 **M0-A 真实 Civ6 观察实验**。这不是 Gate A 批准。规范 v2.1 要求的 E1–E5 与协议行为报告尚未完成；H3/H4/H6/H7/H8/H9/H10/H11 尚未全部裁决。因此 Gate A 仍不批准，M0-B 仍冻结。
