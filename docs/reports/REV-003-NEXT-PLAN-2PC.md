## 1. 资源约束结论

两台电脑足够执行 E2-A、E2-B 和 E3：每轮需要两个独立 Civ6 客户端在同一 LAN 中建房、发现、加入和开局。PC-B 必须安装可运行的 Civ6，且与 PC-A 使用匹配的 Steam Build、DLC 和网络条件。

两台电脑**不足以按现行规范完成 E4**。E4 需要三台电脑/三个玩家端及三端同时抓包，以裁决 H7（mesh/star）并提供 H11 的三人原生与注入对照。不能用模拟 UDP 程序、lanprobe 或把单机抓包拆成三份来替代第三个真实游戏端。若确实最多只有两台 Civ6 电脑，则 E4/H7/H11 保持未验证，Gate A 无法按当前 §11.1 条件通过，除非项目负责人正式修改验收范围并给出新的 H7/H11 验证方法；技术审批员不应自行降低该门槛。

E5 是独立 EOS 构建审计；若没有 Win64EOS 构建，必须标为未验证。Steam 结果不可替代 EOS 结果。

## 2. 第二台电脑的操作方式

### 推荐：PC-B 本地执行端 AI + 本机用户配合

1. 在 PC-B 本机启动该电脑上的执行端 AI，由它按本交接文件负责 PC-B 的游戏操作、注入、抓包和日志归档。
2. PC-A 也由本机操作员/执行端 AI 执行 PC-A 部分。
3. 用户协调同一实验编号、开始/结束时间、房主/客户端角色和刷新/加入动作；两机分别保存原始证据，再通过用户认可的共享目录/介质汇总到项目的 `M0A` 证据目录。
4. 本审批 AI 只基于归档证据复核，不直接远程登录 PC-B，也不需要接收密码、远程桌面凭据或 Steam 凭据。

若 PC-B 没有可运行的执行端 AI，则由用户在 PC-B 按操作表手动执行并保存同等证据。远程控制不是实验的必要条件；关键是两个独立游戏端按共同步骤同步操作并各自记录证据。

### 每台机器的固定准备

- 核对 Civ6 Steam Build ID、游戏 EXE SHA256/版本、DLC、Windows Build、网卡/IP、路由和防火墙；逐机做 E0，不能把 PC-A 的 E0 复制给 PC-B。
- 使用已验收的 civtrace v0.4.4 审计运行模式；不得自行升级 v0.4.5 或修改 Hook/采样格式。
- 将 `civinject.exe` 和 `civtrace.dll` 放到该机器的中立运行目录（避免已报告的项目目录进程枚举异常；其根因仍是执行者归因/推断）。
- 按 README v1.3 的正确参数操作：`-x <游戏进程名>` 无动作参数即注入；`-u` 是停用并结束日志会话，不卸载 DLL。同一进程停用后不能再次启用 Hooks；每次需要新注入状态必须完全退出并重启 Civ6。
- 每轮标记实验 ID、机器角色、PID、注入状态、游戏版本与时间。不得分享账号密码；两机分别使用可正常联机的 Steam 会话。

## 3. 实验顺序

### 阶段 0：双机预检与 E0

PC-A、PC-B 各自完成一次独立 E0，核对版本/DLC/时间/网络接口；两机通过同一 LAN 互相可达。确认 Wireshark/Npcap 抓包可用，测试能在两机同时完整抓包（采集过滤器留空）。若仍无法获得 pcapng，记录为降级证据，不能把 lanprobe 升级为完整抓包替代品。

**交付：** A/B 两份 E0 目录、Build ID 与二进制哈希、网络/防火墙差异表、双端抓包可用性结果。

### 阶段 1：E2-A 被动发现基线（一次全新启动）

- 角色：A 建房并注入（tag=host）；B 不注入。
- 双端完整抓包。B 点刷新，A/B 同时保存 PCAPNG；记录发现请求、房主回复、回复源地址、1104B JSON 样本及其哈希。
- 此阶段只被动观察，不改包。重点回答 F2、H4 被动阶段：是否有响应、地址在源地址还是 JSON 字段中。
- 完成后按 v0.4.4 停用规则停用 A；两台都完全退出 Civ6。

**交付：** 两端 trace（A）、两端 PCAPNG、JSON 原始样本、端点/PID/轮次表、发现包计数与异常记录。

### 阶段 2：E2-B 双端注入生命周期（A/B 均全新启动）

- A 建房并注入，B 加入并注入；两机记录新 PID 和 CIVTRACE_TAG。
- 双端完整抓包。B 执行 10 次刷新；每次记录首广播、末广播、select 结果、成功响应、closesocket。按本机 QPC 计算 T_window 与 T_response；跨机比较只用经校准的抓包时间戳，不直接比较两台 QPC/墙钟。
- E2-A/B 之间不得在旧进程上切换注入状态；两台必须完全退出并重启。

**交付：** 两端 trace/PCAPNG、10 次逐轮数据表、T_window/T_response 分布、丢包/日志 gap/drop 说明。

### 阶段 3：E3 加入与开局（A/B 均全新启动）

- A 建房、B 加入；两端按 README 注入并完整抓包。进入对局持续观察 2–3 分钟，再回主菜单停用。
- 以 socket 句柄、端口和调用者模块将 API 调用归属到 Civ6 数据面；明确检查 62056 的 bind、socket options、send/recv API、OVERLAPPED/PENDING/completion/事件/扩展函数/IOCP 路径。
- 分开统计发现广播与 62056 单播；验证 F3/F4/F6、H3 五分类、H8 socket 选项/数量、H10 生命周期。若 62056 无活动或游戏无法开局，保存失败现场并如实标未验证，不从进程级 API 总数推断数据面模型。

**交付：** 两端 PCAPNG/trace、H3 结构化判定表、62056 流量统计、socket 生命周期表、异常/停用记录。

## 4. 双机实验能回答与不能回答的内容

| 事项 | 双机是否可做 | 边界 |
|---|---|---|
| E2-A/E2-B 发现回复、JSON 地址、窗口时长 | 是 | 两个 Civ6 端，需双端日志/抓包 |
| E3 加入、开局、62056 行为、H3/H8/H10 | 是 | 必须真实进入对局并把调用归属到数据面 socket |
| H5 本机广播回环 | 已有单机限定证据 | 不替代接收回复路径验证 |
| E4 H7 mesh/star 三人方向矩阵 | 否 | 需要第三个真实游戏端和三端抓包 |
| E4/H11 三人原生+注入对照 | 否 | 两人成功不能裁决三人缺陷 |
| EOS 行为 | 取决于 EOS 构建 | 没有 Win64EOS 时标未验证 |

## 5. 审批与工作停止点

1. 本计划只授权准备和执行 M0-A E2/E3，不启动 M0-B。
2. 每个实验完成后，先生成报告、索引、哈希清单并归档原始日志/抓包，再提交本审批 AI 复核。
3. 双机 E2/E3 完成后，更新 v2.1 F/H/R 证据状态；E4/H7/H11 缺第三机时明确列出阻断，不可把双机结果外推为三人结论。
4. Gate A 仅在 §11.1 全部条件有证据支撑后另行提交。若资源限制导致 H7/H11 不可验证，应由项目负责人先提出正式的范围/验收变更，再由技术审批员评估；不能由执行端 AI 静默降级。
