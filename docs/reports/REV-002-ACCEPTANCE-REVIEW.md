## 1. 结论

REV-002 对 R1、R3–R6 的主要整改有源码与测试证据支持，且报告对 Civ6 实验未执行作了正确披露。但 R2 的关键安全保证“所有在途 Hook 已退出后才销毁 MinHook/日志资源”仍不成立：排空超时路径会强行继续销毁资源；计数器也在 Hook 入口的 detour 代码已经开始执行后才递增，存在与卸载线程的入口竞态。因此不能接受“在途 Hook 已显式排空”的结论，工具级安全整改尚未闭环。

另发现报告将 T4 标为 GetExitCodeThread (GEC) 失败，但这只是环境变量 seam 模拟器，未证明 OS API 本身失败处理；该边界在未覆盖项已有披露。报告称“FreeLibrary 返回 0 表示引用计数未降为 0”是错误的 Win32 语义：`FreeLibrary` 返回 BOOL，非零表示成功减引用计数，零表示调用失败。T11 的报告输出显示返回 1，当前源码仅把它打印为“confirmed”而不按 BOOL 解释，随后以模块仍在来推断额外引用；结论方向有可能成立，但该行语义说明必须更正，且需结合独立引用计数测试证明。

## 2. 阻断问题

### B1：在途 Hook 超时后仍执行 MH_Uninitialize 与关闭日志资源

**源码确认。** `civtrace/trace_dll.cpp` `CivTraceShutdown()` 第 1402–1419 行：若 `g_inFlight` 在 5 秒内未归零，仅记录 `force continue`、设 `ok=false` 并 `break`；随后仍 join flusher、执行 `MH_Uninitialize()`、`DrainAndClose()`，最后返回 2。注入器因返回 2 不 FreeLibrary，但 MinHook trampoline/Hook 相关资源和日志文件已被拆除，而在途 Hook 仍可能正在执行并访问这些资源。

**影响推断。** 对仍有活动调用的游戏进程，可能造成 use-after-uninitialize、日志关闭竞态或崩溃；“DLL 映像保留”不足以证明安全，因为 DLL 内 MinHook 与日志资源已被销毁。

**整改要求。** 未排空必须立即停止关闭链，保持 MinHook/日志/队列资源及 DLL 有效，保持 `HS_FAILED`，返回 2 供安全重试；不得调用 `MH_Uninitialize` 或 `DrainAndClose`。需要可控长阻塞 Hook 的测试证明超时后资源保持可用，解除阻塞后重试能够完成安全卸载。

### B2：`g_inFlight` 无法证明 detour 入口竞态已被覆盖

**源码确认。** 各 Hook 先检查 `g_tlsInHook`，再于 detour 函数体第一个普通语句递增 `g_inFlight`，例如 `Hook_socket()` 第 555–558 行；其它 Hook 采用相同模式。MinHook 将执行流转入 detour 后，CPU 可以在执行 `fetch_add` 之前暂停该线程。Shutdown 在第 1398–1403 行禁钩后读到计数为 0，仍可能继续反初始化；该线程随后恢复并继续运行 Hook 代码。

**技术理由。** 在途计数若只在 detour 函数体内递增，不能覆盖“已跳入 detour、尚未登记”的入口窗口。禁用入口和观察计数为零之间需要一个已证明安全的同步协议。若依赖 MinHook 对正在执行线程的暂停/指令指针迁移保证，必须给出所 pin 版本的实现依据并用并发压力测试验证，不能由当前计数器代码单独推出。

**整改要求。** 修正入口登记与 Shutdown 的同步协议，或严格证明并验证 MinHook 的等价保证；增加大量并发调用与反复卸载压力测试，并保证安全证明不依赖“通常不会在几条指令之间被抢占”。

## 3. 需要更正/补证的审计发现

### C1：FreeLibrary 返回值解释错误

`injector.cpp` 第 438–440 行注释写“FreeLibrary 返回 0 表示模块引用计数未降为 0（仍有其它引用）”。Win32 `FreeLibrary` 的 BOOL 返回值表示函数调用成功与否，并不表示模块最终是否仍映射；最终映射状态由 `QueryRemoteModule` 复查。T11 日志中返回码为 1，意味着调用成功；模块仍加载可以与外部引用相符，但不能以返回码 0 来表示“引用未归零”。修正注释/诊断，明确 0 是 API 失败，非零是成功减掉一次引用，然后仅用模块枚举判断是否仍加载。

### C2：完整验收证据仍不是全量独立复现

本复核抽查了报告、`run-T4-gec-fail.txt`、`run-T5-disable-fail.txt`、`run-T11-extra-ref.txt` 与 `run-T13-static.txt`。现有证据是提交的本地输出；本轮未执行 `test-rev002.ps1`、未重建二进制、未用工具重新计算 DLL/EXE 哈希。因此“13/13 PASS”按报告提交证据记录，不能标为本次审批员独立复现。特别地，T4/T5/T6/T10 用环境变量 seam 模拟故障注入；T13 为静态脚本断言，不替代真实并发/系统 API 故障测试。

## 4. R1–R7 复核矩阵

| 项 | 复核结论 |
|---|---|
| R1 卸载状态机 | 主要缺陷已修；code=1 后允许 FreeLibrary、检查 GetExitCodeThread、错误状态不卸载均有源码/报告输出支持。3 次 FreeLibrary 全失败及真实超时未验证。C1 必须更正。 |
| R2 停止与排空 | **不通过**：B1、B2 为阻断问题。 |
| R3 刷盘线程失败 | fail-closed 路径有 SIM 证据；真实线程创建失败未验证。需确保启动失败的同步落盘不会发生在资源未初始化/队列并发状态。 |
| R4 PID 枚举 | 动态 vector 和路径错误显式输出已实现；快照失败未测。 |
| R5 架构/权限探测 | `IsWow64Process` 查询失败 fail-closed 已实现；真实 32 位/权限部分授权未测。任务书提到 IsWow64Process2 或兼容方案，当前选取的 fail-closed IsWow64Process 满足安全目的。 |
| R6 模块枚举扩容 | 扩容并对六次失败返回不可判定，方向正确；极限六次失败未测。 |
| R7 文档与证据边界 | 文案和未验证声明改善；T4/T5 等 seam 证据性质需与结论一致呈现。 |

## 5. 决策与下一步

- **不接受 REV-002 工具整改验收，暂不进入 Civ6 E1–E5。** 在活动 Hook 未排空时继续拆卸资源会破坏取证工具自身安全性，故先修 B1/B2 并更正 C1。
- 整改后提交新报告及绑定哈希的构建/测试证据，重点验证超时保留资源、并发入口登记安全、解锁后重试、安全重复 shutdown 和外部引用场景。
- 工具级验收通过之后，再按 v1.1 README 执行真实 Civ6 E1–E5；这些实验及协议行为报告完成前，Gate A 仍不批准。M0-B 继续冻结。
