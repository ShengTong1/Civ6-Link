### §1.2 更正：22 个回复是 22 个**不同分页**，不是 22 份副本

### §1.3 单页结构（22 页逐字节验证）

| 偏移 | 长度 | 字段 | 实测值 |
|---|---|---|---|
| 0 | 4 | magic | `0x9B696059` |
| 4 | 4 | appid | **289070**（Civ6 Steam AppID） |
| 8 / 12 / 16 / 20 | 4×4 | 未裁决 | 0 / 3 / 1 / 6（本轮常量） |
| 24 | 22 | 房间名（UTF-8 零填充） | `dingzihan2022的游戏` |
| 46 | 106 | 零填充 | 全 0 |
| 152 | 4 | **记录数** | 13 |
| 156 | 4 | **总页数** | 22 |
| 160 | 4 | **页索引** | 0..21 |
| 164 | **938** | 内容 | 记录流 |
| 1102 | 2 | 零尾标 | `00 00` |

**关键修正**：内容区是 **938 B** 而非 940 B。按 940 切分会把每页末尾 2 字节零尾标带进 JSON 中间，导致四条记录声明长度全部偏短、四个 JSON 全部解析失败。按 938 切分后记录框架完全精确：13 条记录恰好消费 19 990 / 20 636 B，尾部 646 B 全零，**4 个 JSON 全部通过 `ConvertFrom-Json`**。

### §1.4 记录流（13 条）

`EnabledGameModeNames`(0) / `EnabledMods`(17 984 B，**45 个 mod** 的 JSON) / `GameSpeed` / `GameSpeedName`(`LOC_GAMESPEED_ONLINE_NAME`) / `GameStarted` / `GameVersion`=`1.0.12.54 (951533)` / `Initialized` / `MapDisplayName`(`LOC_MAP_PANGAEA`) / `MapName`=`Pangaea.lua` / `MapSize` / `RuleSet`=`RULESET_EXPANSION_2` / `RuleSetName` / `SavedGame`

### §1.5 ★ H4 结案：房主地址只来自 IP 源地址

对重组后的全部 20 636 字节做严格 dotted-quad 扫描：**只命中 1 处 `1.0.12.54`（GameVersion 文本，非地址）**。定向搜索 `192.168.31.59`、`26.74.126.98`、`255.255.255.255` 的正序与反序字节，**全部 NOT FOUND**。

→ **载荷不携带房主 IP。客户端只能从回复包的 IP 源地址得知房主地址。**

**方法学声明**：UTF-8 文本区内任意 4 字节都像 IPv4，二进制定宽扫描无判别力，故只采用 dotted-quad 形态扫描。v1 曾报的 27 个 `10.32.32.32` 是 JSON 缩进 `0A 20 20 20` 被误读，已弃用。

### §1.6 方式说明：单机自收

本机同进程建房（绑定 `0.0.0.0:62900`）后，另起 socket 向 `255.255.255.255:62900..62999` 发 1 个 4 字节请求，用 `ReceiveMessageFrom` 收全部完整 1104 B。**无需管理员、无需 pktmon、无需 `--pkt-size 0`、无需第二台机器。**

## §3 对 M0-B 的直接含义（请审计确认这个理解成立）

**Fake-IP 改写只需映射 `sendto` 目标地址与回复源地址，不需要解析或改写这 1104 B 载荷。**

理由：载荷不含房主 IP，客户端要得知房主地址只能靠源地址；因此改写层只要保证"客户端看到的源地址是房主地址"即可，无需触碰载荷内容。

如果这个理解被接受，可以削减 M0-B 的一部分风险面（不需要在 payload 里做字符串/结构替换）。若审计认为需要先验证客户端确实不读载荷地址，请指出需要什么证据。

## §4 四项裁定请求

### 请求 1：H4 的结案方式

**问**：是否接受"单机自收 + 直接观测"作为 **H4 的结案证据**？

**背景**：H4 的问题是"房主地址来自回复包源地址还是载荷字段"。这个问题本身与"有几台机器"无关，单机自收观测的是同一份 1104 B 字节流。但 REV-012 请求项②的原文要求是"双端被动补正"，条件里含"保留房主回复与原始载荷"。

**执行端主张**：H4 的地址来源问题已由本机直接观测回答，证据强度不因单机而降低（观测对象是字节流本身，非跨机行为）。但**E2-A 作为实验条目**仍未满足双机要求。

**选项**：
- (a) 接受单机自收作为 H4 结案证据，E2-A 实验条目另行判定；
- (b) 接受但要求补一次双机被动抓包做交叉印证；
- (c) 不接受，H4 必须由双机抓包结案。

### 请求 3：E2-A 双机补正是否可降级

**问**：E2-A 的双机被动补正，是否可降级为"项目负责人手测（D 级）+ 单机包级证据"的组合？

**背景**：REV-012 裁定 E2-A 需"A 建房注入、B 原生刷新、双端同步完整抓包"。现在实质问题（协议结构、回复存在性、地址来源）已由单机回答，剩下的只是"另一台机器能否看见"这一层——而项目负责人已口述验证过双向房间互见。

**执行端主张**：E2-A 剩余价值主要是"跨机"这一层，且已被 D 级口述覆盖。但**跨机抓包同时会产出 E2-B 需要的素材**，所以合并做可能更经济。

**选项**：
- (a) 降级：D 级手测 + 单机包级证据，E2-A 记为"部分完成"；
- (b) 不降级，但与 E2-B 合并执行（一次双机窗口同时产出 E2-A 补正与 E2-B 数据）；
- (c) 不降级，单独执行。

**执行端建议**：(b)。一次窗口产出两项，减少 PC-B 参与次数。

### 请求 4（路线级）：单机"假房主"实验是否授权

**问**：是否授权构造一个本地"假房主"，让 Civ6 客户端去发现它？

**方案**：绑住 `:62900`，收到 4 字节 `8d e8 fc 70` 请求后，按已解出的结构回 22 页（magic `0x9B696059` + appid 289070 + 页头 + 938 B 内容 + 2 B 尾标）。然后开 Civ6 客户端点刷新，观察它是否把该"房间"列出来。

**能回答什么**：
1. **我们解出的结构是否正确**（客户端是否真的接受）——这是对 §1.3 结构的端到端验证，而不是"看起来自洽"；
2. **客户端视角的 T_response 与 socket 生命周期**（E2-B 的 H6/H9/H10 部分素材）；
3. **M0-B 的最小可行性验证**——如果假房主能被认出，Agent 的 Fake-IP/回环路径就有了可立即测试的原型；
4. 可能会暴露**列表之后是否还有二次握手**（我们目前不知道）。

**边界与风险**：
- 属于**构造报文**，超出当前"被动观测、不得改包"的授权范围 → 必须单独批准；
- 产出的**不是 E2-A 通过、不是联机验证**，只是"协议结构正确性 + 可行性"的单机证据；
- 若客户端在列表之后还要连接查询详情，本次会暴露该缺口（这是好事，但需要额外授权去测）；
- 不触碰真实网卡配置、不运行 metric apply/restore、不注入游戏进程。

**为什么是路线级**：如果这一步成功，**E2-B 可以单机完成**，第二台机器从"每步都要用"降为"只用于 E3 一次真对局"。
