## 1. A-6 复核

### 源码确认

`civtrace/trace_dll.cpp` `Hook_setsockopt()` 第 812–821 行确实将 `val` 初始化为 0，并只在 `optval != nullptr && optlen >= sizeof(int)` 时读取 4 字节。因此对 `optlen=1/2` 的合法调用，当前日志会显示 0，即使首字节为 1；这与“展示性误读”解释一致，且避免越界读取。

归档的 `sobroadcast_c5.c` 逐一测试 optlen 1/2/4 与 val 1/0；`sobroadcast_c6.c` 可在 civtrace 注入下复现 optlen=1、val=1、日志显示 val=0 且广播 sendto 成功。实验设计能区分调用参数的真实首字节与追踪器显示值。

### 证据边界

当前 `docs/diagnostics/a6-sobroadcast-experiments/` 中有 c/c2–c6 源码、PowerShell 脚本及 README，但没有对应的编译日志、运行输出、二进制哈希或完整的 c5/c6 原始日志。故本复核确认的是**代码和推理链可复现**，并把“c5/c6 已得到所述结果”标为执行端报告的测试结果；本审批员未运行这些程序，不能标为独立测试确认。

若要把“游戏的 optlen 确为 1”从推断升级为事实，还需完整 trace 中该 setsockopt 事件的 `optlen` 字段；当前 civtrace 格式没有记录它。c6 证明了 optlen=1 可解释矛盾，不证明游戏具体传入 1。另一方面，在相同 socket 上向 limited broadcast `255.255.255.255` 的 100 次 sendto 均返回 4，是 SO_BROADCAST 已启用的强间接证据；c5 的本机对照增强该推断。建议规范将“游戏实际启用 SO_BROADCAST”标为高置信推断，直到参数长度直接取证或对该 socket 做 `getsockopt(SO_BROADCAST)` 复核。

**处置判断：**无需改 Hook 的安全读取逻辑；在规范/分析中禁止把 optlen<4 时日志的 `val=0` 当成真实值。Agent 广播实现显式开启 `SO_BROADCAST` 是合理要求。

## 2. README 注入命令错误（P1 文档/操作风险）

README §2 表格第 191 行写：`civinject.exe -x CivilizationVI.exe`（不带动作参数=仅查询）。但 `civtrace/injector.cpp` 的参数解析第 263 行起只解析 `-x`、`-p`、`-u`，随后 `unload` 默认 false，并进入“注入”主流程。因此该命令会向选定进程注入 DLL，而非只查询。

这与 README v1.3“移除错误 `-i`，`-x <exe>` 即注入”的说明一致，却与同一 README 的检测进程表格冲突。实验人员按表格做预检查时会意外启动注入，可能污染原生对照或重复实验状态。当前 CLI 没有只查询开关，不应把实际注入命令标成查询。

**整改要求：**把该步骤改成明确的只读 `Get-Process`/`tasklist` 查询（并说明随后注入命令会改变目标状态），或实现单独的 `--list`/`-q` 查询选项并提供测试。无需等待其他整改即可更正文档。
