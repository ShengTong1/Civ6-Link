## §1 已经确立的事实（引用，不新增主张）

### §1.1 广播选路机制与两端修复（C 级，实测）

机制（已在 `REV-010-PEER-ROUTE-RECHECK.md` 与两次独立复现中确立）：

- `255.255.255.255/32` 在**每块网卡**上各有一条等价路由（`Protocol=Local`、`RouteMetric=256`）；
- Windows 在等价路由中取 **InterfaceMetric 最小者**作为源接口；
- 因此"哪块网卡发广播"由 metric 决定，与是否插网线、是否 ping 通无关。

修复前后对照（两端各自独立完成，仅改 `InterfaceMetric`，未改路由表、未改防火墙、未改 IP）：

| 机器 | 修复前观测 | 修复后观测 | 证据 |
|---|---|---|---|
| PC-A | Radmin if18 metric=1（手工设置）< ZeroTier if15 < WLAN if10=45 → 广播走 Radmin | `verify [PASS] if10(WLAN)=100/100` | `broadcast-status-*.txt` |
| PC-B | 800 包 **100%** 走 Radmin | 600 包 **100%** 走 WLAN；游戏本体 `received=796` | `PC-B-单机metric修复与自证-v3.md`（`770C0774…`） |

当前 metric 现状（PC-A，只读观测，本件未做任何变更）：WLAN if10=45/自动度量禁用、Loopback if1=75、Radmin if18=1045、ZeroTier if15=1045、WSL if58=5000、DefaultSwitch if25=5000。

**注**：`set-broadcast-path.ps1` 的 `apply`/`restore` 路径**至今未获授权、从未运行**；上述 metric 值的变化不来自该脚本。本件不涉及、也不请求任何 metric 变更；PC-A 现状保持不自行恢复。

**结论（受限观察）**：在**本机、本实验窗口**内，修改 `InterfaceMetric` 后观测到广播源接口从虚拟接口转到 WLAN。现有材料**不足以**把"房间时灵时不灵的**唯一**根因是 metric"或"中继没有必要"写成普遍结论；PC-B 的 600 包统计仍是**执行端报告、待独立复核**（其 `selfcheck.log`、`game-selfcheck.log`、备份 JSON 与完整 E0 原件尚未归档到本仓库）。

### §1.3 执行端的推断（**主张**，非结论，需裁定）

若 (a) 广播可达、(b) 回复可完整解析、(c) 客户端接受符合该结构的公告，那么"两台同 WLAN 机器互相看到房间"在**协议层面已无未解障碍**——剩下的只是部署层（metric 排错）。

而 **H6 的全部意义**是"发现 socket 存活窗口能否容纳 Agent/Relay 往返 RTT"。**对不注入、不中继的 S1 而言，H6 不是实现本地诊断/离线解析/模拟列表的前置条件**；它仍是任何 Relay / S3 路线的前置实验。（这是对"该前提在 S1 场景下不成立"的限定表述，不是"H6 已无意义"。）

同理 **H3（I/O 模型）**只影响**注入层**（Design I / Design II 的 Hook 是否漏掉真实收发路径），不影响不注入的 Agent 功能（广播诊断、房间列表、健康检查、配置管理）。

首版交付形态三选一：

| 代号 | 形态 | 依赖 | 需不需要第二台机器 |
|---|---|---|---|
| **S1** | **直连助手**：诊断广播源接口 + 一键修正 + 可靠房间列表 + 健康检查。**不注入游戏、不拦截/改写流量、无 Lobby/Relay** | 已解出的 1104 B/22 页结构、`InterfaceMetric` 机制 | 原型不需要（发布前需 C 级双机验证） |

### §2.1 必须同时说明的局限（不掩饰）

S1 明确**不能**做以下事，这些不在本件的乐观表述范围内：

1. **跨子网 / 跨网段不可用**——广播不出网段；不同 VLAN、不同路由器下的两台机器，S1 无能为力。
2. **互联网远程联机不覆盖**——那正是 S3 的场景。
3. **修正 metric 需要管理员权限**——遇到"广播被 VPN 抢走"时，S1 能做的是**诊断并提示**，脚本化修正在多数家用环境需要提权；用户拒绝改 metric 时只能给出手动步骤。
4. **不能伪造房间**——S1 只读真实房主的公告，不生成列表项；"合成公告"能力仅在已授权的实验装置内存在，不进产品。
5. **S1 通过不等于 S3 可行**——H6 仍未测量"有真实响应"的窗口，若将来要做中继，那一步必须重做。

## §4 请求裁定（三项）

### 请求 1（核心）：是否确认首版可交付 S1（无 Hook、无 Relay）？

**问**：是否确认"首版交付形态 = S1 直连助手"，从而 **H6 与 E3 不再是 S1 的阻断项**，而成为 S2/S3 的前置条件？

**选项**：
- **(a) 批准**：S1 成为首版目标，Gate A 第 4、5 项标注为"仅 S2/S3 前置"；
- **(b) 不批准**：维持现范围，先完成 E2-B/E3 再谈首版形态；
- **(c) 有条件批准**：允许按 S1 写**非发布原型**（与 `PROJECT-SCOPE §4` 一致），但 Gate A 阻断项一律不动，等 C 级双机证据再谈"首版形态"变更。

**执行端建议**：**(a) 或 (c)**。

理由：`PROJECT-SCOPE §4` 已经允许"提前开展独立工程原型（Agent 服务骨架、Relay harness、模块接口、本地模拟测试）"，说明"写代码"本身不需要新授权；真正需要裁定的是 **Gate A 阻断项是否随范围调整而重划**。若选 (c)，则现状不变、但执行端可以立刻开工，不会空转。

### 请求 2：D 级手测能否作为 S1 的立项依据？

**事实**：
- 项目负责人两次口述（D 级）："A/B 机器各自建房，对方刷新都能稳定看到房间"；
- 另有 C 级包级证据：广播路径在两端修复后 100% 走 WLAN（PC-B 600/600，PC-A verify 100/100）。

**问**：S1 的立项依据是否**必须**是 C 级双机证据（即必须先做 E2-B），还是"**D 级手测 + C 级路径证据**"已足够支撑"写原型、不发布"？

**执行端主张**：足够支撑**原型**；**发布前仍需 C 级双机证据**（即 E2-B 或等价证据），且该证据不得由本件替代。

### 请求 3：是否授权 P2 有界补充实验（单机：注入了观察工具的客户端 + 已授权合成响应器，同时进行）？

**目的**：现有 H6 数据（3 轮窗口 2013–2021 ms）**全部是零响应轮次**（`recvfrom=0`）。若客户端在收到响应后会**提前关闭发现 socket**，则"中继窗口"的结论会显著改变。P2 用已授权的 responder + 客户端注入 `civtrace`（观察工具，非产品 DLL），测量：有响应时的 `T_window`、`T_response`、`t_close − t_last_response`。

**为什么需要单独授权**：REV-013 §4 授权的是"一次有界合成响应实验"，且条件 5 明写"不注入产品 DLL"；P2 是**第二次运行**且**同时注入观察工具**，属新的组合，故单独请求。

**边界（承诺严格执行）**：
- ≤3 次匹配响应、每次 22 页、每页一次；
- 只回本机源地址，不向任何远端主机发送合成响应；
- 匿名化房间名（记录 fixture 哈希与变更偏移）；
- 不回应后续握手，预算耗尽后仅被动记录；
- **不在房间/对局内注入或停用**，仅主菜单注入、回主菜单后 `-u`；
- 不改网卡/防火墙/路由/metric，不运行 metric apply/restore；
- 产出仍**不是** E2-B，不得表述为联机验证。

## §8 结论

1. **本件的实质**：不是"要求跳过测试"，而是指出 **H6 的阻断性依赖一个尚未确认的前提**——"必须用中继"。该前提在"同 WLAN 直连"目标下不成立。
2. **不改变的事实**：E2-A 仍部分完成；E2-B/E3 仍未完成；Gate A 未批准；M0-B 继续冻结；M0-A 工具仅工具级验收通过。
3. **请求三项裁定**：①首版是否可为 S1；②D 级手测 + C 级路径证据能否支撑原型立项；③是否授权 P2 有界补充实验。
4. **执行端承诺**：裁定前不启动 P2、不写任何注入/中继代码、不改动 Gate 状态；裁定后严格按裁定范围执行，并保留全部原始证据。
