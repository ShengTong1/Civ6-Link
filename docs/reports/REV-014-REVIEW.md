## 1. 首版形态与 Gate 的关系

### 1.1 S1 原型批准范围

批准开始**隔离、非发布的 S1 原型**。第一阶段可实现：

- 只读枚举本机接口、地址、metric、广播路径诊断和健康状态；
- 对现有 fixture 做离线的 1104 B/22 页解析与房间数据模型；
- 使用模拟数据开发本机房间列表 UI。

原型阶段不调用 `Set-NetIPInterface`，不自动修 metric，不运行 metric helper 的 apply/restore，不发送真实发现广播，不从 Civ6 实际 socket 接管响应，不注入、不拦截或改写游戏流量。`InterfaceMetric` 只提供诊断和人工建议。真实在线发现器、自动修复和发布级房间列表需另行定义验收与授权。

该裁定**没有把 S1 变成已批准首版产品形态**。项目范围文件仍承诺 Windows + Steam 双人创建/加入并完成对局；仅当负责人另行变更该承诺时，才可将“纯直连助手”定为发布产品范围。原型可以先做，Gate 与发布标准保持不变。

### 1.2 H6 与 E3

- H6 定义的是发现窗口能否容纳 Agent/Relay 往返。对无 Relay、无注入的 S1 原型，H6 不是实现本地诊断、离线解析或模拟列表的前置条件；它仍是任何 Relay/S3 路线的前置实验。
- E3/62056 属于游戏数据面和注入路径审计。它不阻止开发只读 S1 原型，但仍是原项目 Gate A 条目，并且在宣称 CivLink 支持真实双人加入/开局前，必须取得真实双机对局证据。不得仅凭“标准 LAN 理应直连”代替验收。
- E2-B、E3 仍标为未完成；它们在本次裁定中没有被标为通过、豁免或从 Gate A 删除。

## 2. 证据采信和需更正的表述

1. 本机独立探针的 100/100 WLAN 发现包和 PC-B 执行报告中 600 个游戏包的统计，可支持“所报告的测试窗口内观测到 WLAN 路径”的原型假设；PC-B `selfcheck.log`、`game-selfcheck.log`、备份 JSON 和完整 E0 原件尚未在当前仓库回传，因此 PC-B 结果仍是**执行端报告、待独立复核**。
2. “修改 InterfaceMetric 后本机广播路径从虚拟接口转到 WLAN”可作为受限的、按主机和实验窗口描述的观察。现有材料不足以把“房间时灵时不灵的唯一根因是 metric”或“中继没有必要”写成普遍结论。房间互见只来自项目负责人手测，仍是 D 级。
3. REV-014 §1.2 的“地址只来自回复包 IP 源地址”超出 H4 已批准结论。应使用 REV-013 的限定措辞：**当前样本的已分析载荷未发现房主 IPv4 字段；本次抓包观察到回复源 IP 是地址通道。** 不能推成客户端只能使用源地址。
4. REV-014 §3 的 Gate A 第 1 项“基线可比完成”与当前权威范围文件不一致。仓库仅有 PC-A E0 基线；PC-B E0 及原件仍待回传，因此 Gate A 第 1 项保持未完成/部分完成。
5. REV-014 中 “`cargo 1.99.1` 可直接用”未获本机验证。当前环境 `cargo --version` 因未配置默认 toolchain 而失败；显式 `cargo +1.75.0 --version` 可用，Node 为 v24.21.0。可用明确的 1.75.0 toolchain 开始最小 Rust 2021 骨架并验证依赖，不得把 1.99.1 写成本机实测版本。

## 3. 原型开发约束

- 代码放在与发布产品分离的 prototype/workspace；第一阶段以离线 fixture 和 mock UI 为准。
- 不引入自动 metric 修改，不调用管理员提权，不更改 NIC、路由、防火墙或游戏配置。
- 不把单机合成公告列表称作 Civ6 原生房间列表已可靠工作；只有真实双机正向发现、加入和进入对局的证据才支持端到端产品声明。
- 原型不能冻结 Fake-IP 地址段、协议格式、密钥协议或 Relay 架构；也不能以此宣布 M0-B 开始。

## 4. P2 有界组合实验授权

批准**一次**本机 P2：在 Civ6 主菜单运行观察工具 `civtrace.dll` v0.4.4，同时启动 `synthetic-host-responder.ps1` v2.2，观察有响应时的 `T_response`、`T_window` 及 `t_close − t_last_response`。该实验用于补充判断“收到响应后客户端是否提前关闭发现 socket”，不是跨机 H6/E2-B 验收。Responder 当前 `Socket.Select` 的异常分支仍静默 `continue`（约第 235–238 行）；**执行前须把该分支改为记录异常/计数并使汇总可见**。现有 9/9 测试覆盖 ReceiveMessageFrom 错误，不覆盖 Select 错误。该项完成前不得启动 P2。

### 执行边界

1. 只在单机主菜单做；不进 LAN 房间、不加入对局、不在游戏中注入或停用。确认进程 PID、游戏版本、DLL/EXE 哈希、日志会话头后再刷新。
2. 最多 3 次匹配响应，每次 22 页、每页一次；测试应使用不超过 3 次刷新，并将相邻刷新间隔与 responder 的 burst window 记录清楚。只回应本机来源，不回应二次握手。
3. responder 运行前检查发现端口；不使用 `SO_REUSEADDR` 争用 IPv4 端口，不杀占用进程。实际占用端口需记入证据与分母。
4. 只注入 `civtrace.dll` v0.4.4 观察工具，不注入产品 DLL；不修改游戏文件、网卡、metric、路由、防火墙、Steam 配置。不得调用 metric helper apply/restore。
5. 记录每轮 UI 刷新时间、匹配请求端口、逐页发送时刻和哈希、civtrace 中对应 socket/handle 的首末事件、close 时刻及原始日志。报告中区分观测事实、派生时间和推断；计时以同机单调时钟/抓包时钟配对，不把墙钟当精确毫秒源。
6. 回到主菜单后按 civtrace v0.4.4 审计运行模式停用；若 shutdown 返回超时码 2，保留资源，不强制 FreeLibrary 或强杀游戏，允许正常退出进程并归档失败路径。
7. 不为本次 P2 强制要求 pcapng/UAC；若无法取得高精度同机配对时序，先如实标“时间精度不足”，不得扩大结论。

P2 结果只能作为单机、有合成即时响应条件下的补充时序观察；不能代替 E2-B 的两端多轮分布、真实房主响应或 E3。
