## 阻断项（如有，B-1..B-n，每条含：问题/证据/为什么阻断/修法建议）

### B-1 §5.3 L170「从 L 发出 ⇒ 保证客户端看到的源 = 房主IP:P」是不可提供的保证，而它是整个跨机方案的关键连接点

**问题**
文档 L170 原文：「**从 `L` 发出**，保证客户端看到的源 = `房主IP:P`（与它发包的目标端口一致）」；§3 L49 同义。这里把两件事混为一谈：
- 源**端口** P：成立。L 确实 bind 在 `0.0.0.0:62901..62999` 的具体端口上（`main.rs` L751–L753 `for port in plan_discovery_ports(..) { UdpSocket::bind(addr) }`），从 L 发出的包源端口必为 P。
- 源**IP**：不成立，且不是"实现细节"，而是无法由"从 L 发出"推出。L 绑的是通配地址 `0.0.0.0`（文档 L139–L147 的注释也明确"MUST be bound to 0.0.0.0"）。通配绑定的 UDP socket 在 `send_to` 时**不携带源地址**，源 IP 由 Windows 的源地址选择 / 路由表在发送那一刻决定，与 socket 的绑定地址无关。

更要紧的是"房主IP"本身是歧义的：本机有 WLAN `192.168.31.60`、Radmin `26.74.126.98`、ZeroTier `192.168.191.3` 三个地址，**没有单一的"房主IP"**。客户端能接受的是"与它同网段的那个地址"，这只能靠路由选择去命中，而设计从未采集"请求是从哪个接口/哪个目的地址进来的"这一信息。

**证据**
1. `M0A/c2-egress-v3-results.txt`（552 B）是同一 agent、同一通配 socket 的实测：`baseline … replySrc=192.168.31.60:62900`、`radmin … replySrc=26.74.126.98:62900`、`wlan … replySrc=192.168.31.60:62900`。**核对结论：这不是"回错了网卡"的反例，恰恰是"源 IP 随路由跟随客户端所在网络"的证据**——radmin 场景里客户端自己把出接口钉在 Radmin（`M0A/c2-b-send1-v3.ps1` 用 `setsockopt(s, 0, 31, htonl(ifIndex))`），所以回包源变成 Radmin 地址是**正确**的。本审计明确否定"客户端来自 WLAN 就会收到 Radmin 源"这一读法（那种情形需要同子网多归属或非对称路由才会发生，**未验证**）。
2. 但上述实测同时证明：源 IP 完全由路由决定，**设计没有任何手段保证或验证**它。缺口出现在：① 同子网多网卡（WLAN + USB 以太网同为 `192.168.31.0/24`，Windows 可能从另一块卡选源）；② 非对称路由（广播从接口 A 进来，回程路由走接口 B）；③ 多宿主 + 策略路由 / 双默认网关。这些情形下客户端会收到一个"它不认识的网段地址"，或者用到不了的地址。
3. 为什么源 IP 一旦错就必然失败：§4.3 已实测 22 页内**不含** `127.0.0.1`（`127.0.0.1 bytes present in any page: False`）也不含 `192.168.31.60`（`LAN 192.168.31.60 present: False`）；`C3-fullchain-20261118-2240/summary.json` 的 `room_name_hex` 也只承载房名。既然广告页不携带房主地址（**推理，真机未证实**），客户端只能从 `recvfrom` 的源地址得知房主在哪，随后用它去连 62056 会话面。源 IP 错 ⇒ 列表里显示一个错地址，或直接丢弃 ⇒ 进房必败，而失败点在 62056 阶段，症状与"只修发现不修 62056 = 白修"（研究文档 L41/L456）叠加，排障极难。
4. C3 证据体系天然测不到这一点：`c3-probe-result-1.txt` 全部是 `from=127.0.0.1:62900` / `reply source 127.0.0.1:62901`，loopback 上源地址恒为 `127.0.0.1`，这个 bug 在单机证据里永远不可见。`M0E-completion-20261118-234320/summary-run1.txt` 的 `reply source : 127.0.0.1:62901` 同样如此。

**为什么阻断**
- 文档把"从 L 发出"当成充分条件，写出了"保证"二字。后续实现与真机验证会按这个错误前提去做，**验证清单里就不会出现"回包源 IP 是否正确"这一项**（§8 L210–L216 五项里确实没有）。
- 修它要动 socket 架构（见修法），属于"现在改还是以后重写"的分叉，不该带进实现阶段。
- 它不是"未验证"，而是**已知有反例路径、设计上无手段**。设计文档不能对无法提供的能力写"保证"。

**修法建议**
1. 首选：接收侧用 `WSARecvMsg` + `IP_PKTINFO` 拿到每个 magic 的**目的地址**，发送侧用 `WSASendMsg` + `IP_PKTINFO` 把源地址显式钉成该目的地址，实现"从哪来、回哪去"的严格对称。代价：`civlink/agent/Cargo.toml` 的 `[dependencies]` 目前**完全为空**且要求 `cargo +1.75.0 build --offline`，`std::net::UdpSocket` 不暴露这些 API ⇒ 要么手写 `extern "system"` 绑定（ws2_32 已在链接范围内），要么加 socket2/winapi 依赖并放弃离线零依赖约束。这个取舍必须写进设计。
2. 次选：**按接口分组 socket**。62901–62999 由 agent 独占（研究文档 L304、L156 只对 62900 有劫持风险），完全可以在每个本地具体 IP 上各 bind 一组（`192.168.31.60:62901..62999`、`26.74.126.98:62901..62999`、`192.168.191.3:62901..62999`），从具体 IP 绑定的 socket 发出的包源地址就是该 IP。客户端从哪个网段来，就用该网段的 socket 回。代价：socket 数 × 接口数（3 × 99 = 297，仍在 Windows 句柄量级内），且需要枚举接口变化（WLAN 重连、ZeroTier 上下线）时重建。
3. 无论哪种，都必须：① 把 L170 的"保证"改为"由路由/显式源地址决定，见 §X 机制"；② 在 §8 增加"多网卡/同子网多归属/非对称路由下回包源 IP 正确性"的必测项；③ 回包前记录实际源地址（`WSASendMsg` 可拿到）并写入 summary，便于真机排障；④ 在客户端侧用 `recvfrom` 校验源 IP 与预期一致，作为自测断言。

### B-2 §5.3 L173 / §5.4 L189 宣称的「去重 + 总阻塞 ≈ 1×timeout」在随附实现中不存在；后果不是 agent 慢 1 秒，而是让真实游戏为一次刷新生成 99 份完整广告并全部灌进一个 64 KB socket

**问题**
文档 L173：「**对策**：去重仍按 `(client_ip, client_port)`：同一客户端的一次刷新只处理**第一个**到达的 magic，其余 99 个仍按"已应答"跳过……因此**每个客户端刷新只触发一次重放**，总阻塞 ≈ 1 × timeout」；L196 再次确认「去重键与 `answered` 表复用（保持 100 包只答一次的语义）」；L189 给出的调用是 `comp.handle(&self.listeners[i], &buf[..len], &from, &mut self.answered)`。

实现与这三处全部不符：
- `main.rs` L617：`fn handle(&mut self, listener: &UdpSocket, magic: &[u8], client: &SocketAddr) -> CompletionOutcome` —— **三参，没有 `answered` 形参**。L189 的四参调用在代码里不存在。
- `main.rs` L838–L860 的 completion 分支：`if is_discovery_magic(..) { if self.completion.is_some() { let mut comp = ..take()..; let outcome = comp.handle(&self.listeners[i], ..); .. self.completion = Some(comp); handled += 1; continue; } }` —— **没有 `self.answered` 查重，没有 insert，没有 `max_replies` 预算**。`continue` 回到 `loop`，同一个 socket 上连到的 magic 会被连续处理。
- 对照非 completion 路径 `consider()`（L914–L962）：`key = (ip.to_be(), src_port.to_be())`、`if self.answered.contains_key(&key) { return Skipped }`、`replied_sockets >= max_replies` 预算、L952–L954 只在整轮发送成功后 `answered.insert(key, true)` —— 文档描述的那套去重**只存在于旧路径**。

**后果（按真实报文量算）**
一次"刷新"是客户端向 `62900..62999` **每个端口各发 1 个** magic（研究文档 L13），源端口**固定**（同 L13），二层广播 + 三层广播各一份 ⇒ 落在 agent 的 99 个监听端口上的是 99 个 magic（可能更多）。当前实现每个 magic 都完整走一遍 `handle`：

1. `handle` 先 `forward.send_to(MAGIC, 127.0.0.1:62900)`（L619–L629）⇒ 真实游戏收到 99 个探测，**每个都会生成一份完整 22 页广告**。合计 99 × 22 × 1,104 B ≈ **2.41 MB / 2,178 个 UDP 报文**，全部回到同一个 forward socket（`bind("0.0.0.0:0")`，L596–L597，全生命周期只建一次）。Windows 默认 UDP 接收缓冲约 64 KB ≈ 2.6 份广告，**必然溢出丢包**。
2. 溢出 ⇒ 后面的 `handle` 收不满 22 页 ⇒ 走 L664–L673 的 `pages.is_empty()` 分支记 `timeouts` 并 `GameSilent`（不应答），或走 L674–L678 的 `short replies` 分支**把残缺广告转发给客户端**（注释 "Forward it anyway"）。两种都是坏结果：客户端要么什么也收不到，要么收到解析不了的半份广告。
3. 跨轮串包：forward socket 跨轮复用且从不排空。第 N 轮超时留下的页会被第 N+1 轮当作自己的应答读走（内容碰巧相同所以不显形，但统计失真；一旦房主换房/换图，就会把旧广告发给新客户端）。
4. 阻塞量级：游戏有房且健康时每轮只是"发一包 + 读 22 页"，量级是毫秒；**游戏静默（没建房 / 最小化卡顿 / 防火墙拦住 loopback）时每轮走满 `set_read_timeout` = `--completion-timeout-ms`（默认 1000 ms，L1647、L1724–L1735）**，99 轮串行 ⇒ `poll` 阻塞约 **99 s**。而 `poll` 是 agent 主循环里的唯一 drain 点（L2099–L2118），它一卡，99 个发现端口、CVLH2 帧 socket、peer 转发全部停摆。文档 L172 自己写了"最坏 100 × timeout"再靠去重把它驳回，而这个去重不存在。
5. 即使按文档补齐去重，"总阻塞 ≈ 1×timeout"也只是**单客户端**结论；多客户端并发、或异常客户端用多个源端口发同一刷新，仍是 `N × timeout`（文档 L236–L238 已经把这几个场景问出来，但没答）。设计缺少**全局预算**。

**证据**
- 代码：见上（`main.rs` L617、L838–L860、L914–L962）。
- 自测覆盖不到：`M0A/captures/M0E-completion-20261118-234320/summary-run1.txt` 记录 `requests seen : 1`、`replays sent : 1`；`verdict.txt` 是 `checks : 27/27`，但 27 项里没有"一次刷新 99 个 magic"这一项，也没有"多端口并发时阻塞上限"。也就是说自测只证明了"1 个 magic → 1 次重放 → 22 页"，恰好是**最不容易暴露该缺陷**的那条路径。
- 文档自相矛盾：L173 说"总阻塞 ≈ 1 × timeout"，L172 说"最坏 100 × timeout"；两者只能有一个是设计约束，文档没说清哪个被采纳，而代码两个都不满足。

**为什么阻断**
- 它把设计目标直接反转：本工具存在的意义是"让客户端搜到房"，而这条路径会让客户端在"游戏有房"的最常见场景下收到截断广告、在"游戏无房"时把 agent 卡死 99 s。
- 它给真实游戏进程引入了 99× 的应答放大负荷。Civ6 的发现应答器是否线程安全/可重入**未验证**，但在同一瞬间喂它 99 个请求属于设计不该造成的风险。
- 修它要动 `poll` 的调度模型（增加刷新 epoch、总预算、每 socket drain 上限），是设计层改动，不是补几行代码。

**修法建议**
1. 恢复"一次刷新只重放一次"的语义，但主键不要用 `(client_ip, client_port)`（客户端每轮换源端口，研究文档 L161/L439，用端口做主键只能区分"这一轮/下一轮"，不能合并同一轮的多个端口）——正确做法是**刷新 epoch**：任一端口收到首个 magic 起，开一个 `epoch`（例如 300 ms 窗口），窗口内其它端口上来自同一源 IP 的 magic 直接吞掉并计数，窗口结束才允许下一次重放。
2. `handle` 传绝对 deadline（`Instant::now() + timeout`），在循环顶部与 `continue` 分支都检查，保证单次严格 ≤ timeout。
3. `poll` 加每轮总预算（例如每轮最多 1 次 `handle`），其余 magic 丢弃并计入统计；对每个 listener 每次 poll 的 drain 数设上限（例如 8），避免单端口饿死其它端口。
4. `--completion-timeout-ms` 上限从 60,000 收到 ≤ 2,000（配合 B-2 修法后可再评估）。
5. 每次 `handle` 前后**排空 forward socket**（非阻塞 drain 到 `WouldBlock`），消灭跨轮串包。
6. 在 §8 增加"阻塞期漏收率 / 多客户端并发下的单轮阻塞上限"必测项，并在自测里加"一次刷新 99 magic"的用例。

## 高风险项（H-1..H-n）

### H-1 §5.3 L167 的「防串扰」不够：只比源 IP 不比源端口，且任意长度都当广告页转发 ⇒ 同机任意进程可向客户端注入任意内容

**问题**
文档 L167：「只接受**源地址 == game_addr 的 IP** 的包（防串扰）」；`main.rs` L641–L646 严格照做：`if from.ip() != game_ip { continue; }`，**从不检查 `from.port()`**，并且 `if len != SIM_PAGE_SIZE { odd += 1; }` 之后照样 `pages.push(buf[..len].to_vec())` —— 任意长度（0 < len ≤ 4096）都会被当作一页转发。

**后果**
1. 本机任意进程向 agent 的 forward socket 端口（`0.0.0.0:<临时端口>`，可被枚举）发任意 UDP 包，只要 `from.ip() == 127.0.0.1`（同机默认就是），就会被 `pages.push` 当成广告页，随后 `listener.send_to(page, client)`（L681–L689）转发给客户端。**攻击者可以决定客户端看到的房间名/地图/版本字符串**，即让 agent 成为"伪造协议内容"的通道——虽然 agent 自己不生成字节，但硬约束"不得伪造协议应答内容"的意图被绕过。
2. `continue` 分支不推进 deadline：`while pages.len() < self.max_pages` 的唯一退出条件是"收满"或 `recv_from` 自身超时/出错。攻击者以小于 timeout 的间隔持续发包（包括 `len == 0` 的包——L643 `if len == 0 { continue; }` 既不 push 也不计数），即可让单次 `handle` 无限延长。`max_pages` 最大可设 256（L1736–L1745），攻击者可让单轮收 256 个伪造页。
3. 真机场景并非纯理论：任何本机进程（含游戏 mod、显卡工具、其它"网络加速器"）都能触发；而客户端的房间列表会直接呈现这些内容。

**修法**
- 必须同时校验 `from.port() == self.game_addr.port()`（游戏应答源端口就是它监听的 62900；loopback 重放下这一点稳定）。
- 长度必须严格 `== SIM_PAGE_SIZE`（本设计就是"原样转发游戏应答"，没有理由接受其它长度；若为兼容未来版本，应做成显式开关并单独验证）。
- `continue` 改为"计数 + 超阈值 break"：不匹配包累计 N 次（如 `max_pages * 4`）或超过 deadline 即退出，并把计数写进 summary。
- 在 §8 增加"同机第三方进程注入"的验证项（当前完全缺失）。

### H-2 §5.1 L132 / L133 与实现语义相反，按文档写命令必然启动失败

**问题**

### H-3 反射/放大：1 个 4 字节 magic → 22 × 1,104 = 24,288 字节，约 6,072×

**问题**
completion 模式下，任何源发来的 4 字节 magic（只要命中 62901–62999 中任一端口）都会触发一次 loopback 重放并把 22 页回给来源地址（L681–L689 直接 `send_to(page, client)`）。放大倍数 ≈ 24,288 / 4 ≈ **6,072×**，且 UDP 源地址可伪造、无握手。局域网内任意主机可用伪造源把 2.4 MB 流打到受害者。

**与既有路径的关系（必须说清，避免夸大）**
既有的 fixture 路径（`--simulate`）同样是 22 页，放大倍数相同，因此这**不是 completion 全新引入**的放大面；但 completion 把它变成了"无需 `--simulate` 即可触发、且内容是真实广告"的形态，触发门槛更低、且更容易被误认为合法房间。文档 §7 的五条边界（L204–L208）完全没有提到放大面。

**修法**
在 §7 增加"反射放大"边界并显式取舍：① 源地址白名单（仅接受 RFC1918/ULA 的发现请求）；② 每源 IP 限速（如 1 秒内最多 1 次重放，配合 B-2 的刷新 epoch）；③ 或明确写下"接受该风险，因为目标端口/网段受限"。三者都可以，但不能不写。

### H-4 「房主必须能随时重新建房」的保证依赖用户手写 `--reserve-62900`，在 completion 之外的路径上不成立

**问题**
`plan_discovery_ports(reserve_62900)`（L713–L717）在 `reserve_62900 == false` 时**会包含 62900**，即 agent 会 bind `0.0.0.0:62900`。completion 模式靠 L1870 强制要求该 flag，因此 M0-E 路径是安全的；但 `--sim-lan-listen` 单独使用时没有这层保护。若 agent 先启动并占住 62900，游戏随后 bind 会失败/被劫持，房主无法建房——这正是硬约束第 4 条要防的事，只是被一个用户可能忘记的 flag 挡住了。

**补充**：实现 L764–L769 对 bind 失败只 `stats.bind_fail += 1` 并 eprintln 跳过，若用户把 `--sim-lan-listen` 指向具体 IP（如 `192.168.31.60`）而该端口已被游戏占用，agent 会静默少绑端口、不报错，表现为"某些端口不响应"，同样难排障。

**修法**
把 `--reserve-62900` 改为**任何 `--sim-lan-listen` 模式下的默认行为**（保留 `--allow-62900` 之类显式反选给实验用），并在 summary 里把"62900 是否被本进程持有"作为一等公民输出（当前 L735–L743 只是 eprintln）。

### M-1 `--completion-max-pages` 允许 1..=256，< 22 时会把截断广告发给客户端；"按长度分桶"在实现里不存在

文档 L167 说「长度在 `[SIM_PAGE_SIZE-?]` 范围内接受任意长度（不硬编码 1104，兼容版本差异，但计数分桶）」。实现：L641–L646 任意非零长度都 push，只把 `odd_page_sizes` 加一（L558、L547–L559 的 9 字段结构体里就一个 `u64`，**没有分桶**）；L1736–L1745 允许 1..=256；L674–L678 在 `pages.len() < SIM_PAGE_COUNT` 时仍 `Forward it anyway`。

## 逐条回答 §11 的 7 个问题

**Q1（L238）同步阻塞是否可接受？去重保证"每次刷新只重放一次"是否足够（同一客户端连续多次刷新、多客户端并发）？**

不可接受，去重保证也不足够——而且它当前根本不存在（B-2：`main.rs` L838–L860 无 `answered` 查重，文档 L189 的四参签名在代码里没有）。逐场景：
- **同一客户端连点刷新**：客户端每轮换新临时源端口（研究文档 L161/L439），`(client_ip, client_port)` 主键对"同一轮"有效（同一轮 100 包源端口固定，研究文档 L13），对"下一轮"必然失效。所以"每次刷新只重放一次"这句话在**单轮内**成立、在**跨轮**必然每次重放——这是设计使然，但文档没算总账：用户点 5 次 = 5 次重放，游戏静默时 5 × 1 s。
- **多客户端同时刷新**：`N` 个客户端 = `N` 次串行重放，阻塞 `N × timeout`，无全局预算。
- **一个客户端用不同源端口连发**：主键不同 ⇒ 每次都重放，可被滥用（配合 H-1，还能让游戏被要求生成 `N` 份广告）。
- **无去重时的真实量级**：99 个端口各一次 = 99 次重放 = 游戏侧 2,178 个报文 / 2.41 MB 涌入同一 64 KB 缓冲 + agent `poll` 阻塞最多 99 s。这个数字必须写进设计。
结论：必须引入"刷新 epoch + 绝对 deadline + 每轮总预算 + 每 socket drain 上限"，并把 timeout 上限收紧。

**Q2（L239）fail-closed 是否正确的产品选择？还是退化到 fixture？**

fail-closed 正确，退化到 fixture 错误。理由：fixture 是 agent 自己生成的广告，直接触碰硬约束"不得伪造协议应答内容"；更糟的是它制造"列表里有房、点进去进不了"的假阳性，用户会更难判断到底坏在哪。宁可什么都不显示。
但存在更好的第三条路，且已部分实现：**降级而非静默**。① 现在 L674–L678 对"部分页"是 `Forward it anyway`（转发残缺广告），但只在 summary 里记 `short replies`。应当在 agent stderr / GUI 里明确"本次只拿到 N/22 页，列表可能不完整"，让用户看到因果。② 游戏完全静默时 `GameSilent` 只 `timeouts += 1`，建议升级为可诊断状态："本机游戏未在 62900 应答"——这恰好能把"房主没建房"/"游戏没启动"/"被防火墙拦"区分开。③ 产品侧提供"房主自检"入口（一键向本机 62900 发 magic 并显示是否有 22 页应答），把猜测变成测量。④ 未来若要缓存，§4.4 已证明内容确定、可缓存，但必须先过"换房/换图后缓存失效"这道验证（见 Q7）。

**Q3（L240）只接受源 IP == `game_addr.ip()` 是否足够？是否会漏掉游戏从其它地址回包？**

不够（H-1），但"游戏从其它地址回包"这个担心已经被实现用另一种方式消掉了，需要分开说：
- **不够的部分**：只比 IP 不比端口 ⇒ 同机任意进程可注入伪造页、可无限拖长单轮。必须加 `from.port()` 校验与长度校验。
- **跨版本地址漂移**：实现把 `--game-discovery-addr` 强制为 loopback（L591–L595、L1885–L1895），所以"游戏只监听 LAN IP 而回包源是 LAN IP"的情形根本不会发生——方向对，但代价是"若某版游戏不在 loopback 应答，本设计直接失效"，这条要进 §8。另一个真实风险是 IPv6：若未来游戏在 `::1` 应答，`from.ip() != game_ip` 会全部丢弃，表现为"永远 GameSilent"。
- **建议**：校验 `(ip, port)` 元组；对不匹配包计数并在 summary 单列（现在 `continue` 什么都不记，真机上"到底有没有回包"无法判断）；把"预期源地址"做成可配白名单（允许本机具体 IP），而不是硬编码 port 匹配到 loopback 唯一解。

**Q4（L241）强制 reserve 是否应允许用户覆盖？**

**不应允许覆盖**。绑 62900 会触发 `SO_REUSEADDR` 单播劫持（研究文档 L156 实测："单播到 192.168.31.60 → 只有代理收到，游戏 nothing"），直接破坏"房主必须能随时重新建房"。这一点设计判断正确，L206 的表述也对。
但**实现方式**应改：文档 L133 承诺"自动生效"，实现 L1870 是"报错要求用户加 flag"。前者是"强制语义"，后者只是"强制用户"。二者都满足硬约束，但后者让"忘了加 flag"变成启动失败，用户体验与文档承诺不符（H-2）。另见 H-4：completion 之外的路径没有这层保护，`--reserve-62900` 应成为 `--sim-lan-listen` 的默认。

**Q5（L242）`--completion-max-pages` 与"不硬编码 1104"之间是否有隐患？**

有，且比文档自认的更重（M-1）：① `max_pages < 22` 会转发截断广告且无提示；② 实现**没有分桶**，只有一个 `odd_page_sizes` 计数，任意长度都会被当作一页转发给客户端；③ 没有页序号校验（第 N 页的序号字段未检查），也没有页数协商，一旦版本变 24 页，默认 22 会静默截断。
建议：`max_pages` 改为"上限保护"而目标值（按 deadline 收，不按页数停）；`< SIM_PAGE_COUNT` 拒绝启动；把"必须 1104 字节且首 4 字节 `59 60 69 9B`"作为硬校验（这正是"不伪造"的延伸：只转发能确认是游戏广告的字节）；分桶至少要能区分"全 22 页都 odd"与"1 页 odd"。

**Q6（L243）与 B1（`--sim-real-capture`）互斥的处置是否正确？**

正确。两条路径都试图在"magic 到达"时产生应答，同时开启时行为取决于 `poll` 里的分支顺序而非设计，属于不可判定状态；互斥是唯一干净选择。实现 L1861–L1866 已落地，报错文案准确。唯一建议：补一个单测覆盖该互斥（连同 H-2 的另外 3 条规则）。

**Q7（L244）§8 未验证项是否完整？**

不完整。现有 5 项（跨机真实链路、真客户端是否接受"源端口 = 请求目标端口"、22 页丢失容忍、真客户端端到端、≥3 客户端并发）方向对。缺失的 6 项（都是"必须实测才能进发布"的）：
1. **多网卡/同子网多归属/非对称路由下回包源 IP 的正确性**（B-1 的核心，`c2-egress-v3-results.txt` 已显示源 IP 完全由路由决定）。
2. **99 端口阻塞期的漏收率与主循环停顿**（B-2；需在真机上量 `poll` 单次耗时与 `bind_fail`/丢包）。
3. **同机第三方进程注入/放大**（H-1、H-3：本机任意进程能否让客户端显示伪造房间）。
4. **`--completion-max-pages < 22` 时真实客户端的行为**（是丢弃、报错，还是显示半份房间）。
5. **房主换房/换图/装 mod 后广告内容的变化与确定性假设的边界**（§4.4 的"确定性"只在本轮同房状态下成立；缓存若将来启用，必须验证失效条件）。
6. **Windows 防火墙/安全软件对"回包源 ≠ 请求目标 IP"的处理**（B-1 的下游：即使源 IP 正确，也要验证防火墙放行；若源 IP 错，也要知道是被防火墙丢还是被客户端丢）。

## 是否允许进入实现阶段

**否。**

理由：本设计的机制核心（loopback 重放 + 原样转发）已被 C3 实测与 M0E 机械自测证实，方向正确、边界纪律也守住了（不伪造、不绑 62900、不碰 62056、明确声明非双机结论——这些值得保留）。但进入实现前必须先解决两处**设计级**问题：

1. **B-1**：§5.3 L170 的"保证源 = 房主IP:P"必须换成可实现的机制（`WSASendMsg` + `IP_PKTINFO` 显式源地址，或按接口分组 socket），并在文档里写清零依赖约束下的取舍。这是唯一决定"跨机到底能不能成"的环节，且本机 loopback 证据永远测不到它。
2. **B-2**：恢复"一次刷新只重放一次"的设计语义（刷新 epoch + 绝对 deadline + 总预算 + forward socket 排空），并把 §5.3/§5.4 的代码级描述改成与实现一致。当前形态下，一次刷新会让真实游戏生成 99 份广告（约 2.41 MB）灌进一个 64 KB 缓冲，并可能把 `poll` 卡住 99 s——这会把本工具要修的症状原样造出来。

放行前置条件（建议按序）：
- [ ] B-1、B-2 的设计文本改完，附上选定机制的取舍说明（含 Cargo 零依赖约束的处理）。
- [ ] H-1 的源过滤（端口 + 长度 + 不匹配计数 + deadline 推进）与 H-4 的 62900 默认保护写入设计。
- [ ] §5.1 的 L132/L133 与实现语义对齐（H-2）；§5.4 的签名与 §5.2 的字段按实现回写（M-2）。

- [ ] 补 completion 路径的 5 类单测（M-3），并在自测里加入"一次刷新 99 magic"与"多客户端并发"用例。
- [ ] 文档冻结：写明对应的 agent 二进制 sha256，把 `M0E-completion-*` 的 27/27 自测结论纳入 §4/§10（L-3）。
- [ ] 修正 L174 的"毫秒级"（M-4）与 §4.5 的跨机括号（M-5），把无法由本机证据支撑的断言移入 §8。
