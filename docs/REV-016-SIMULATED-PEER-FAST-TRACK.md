- 日期：2026-11-13
- 负责人指示：不把第二台装有 Civ6 的电脑作为继续开发的前置；按已反复验证的代码模拟房主路线推进。
- 目标形态：Windows + Steam + 双人；游戏适配层采用 DLL 注入作为当前产品目标；Fake-IP 与 Relay 保留。
- 本文用途：**取代旧计划中“等待第二台 Civ6 电脑到场后才继续开发”的执行顺序**。旧报告、原始证据和 Gate 判据保留，不删除、不改写为已通过。
- 状态：路线批准；下列技术里程碑仍须逐项验证。本文不批准 Gate A/B，也不宣称真实双机联机完成。

---

## 1. 已知起点与证据边界

项目负责人报告：DSH 执行端的代码模拟房主已多次被本机 Civ6 局域网列表发现。该事实可作为本阶段**客户端发现集成的开发夹具**。现有归档也包括单机合成公告实验：本机构建接受合成公告并显示列表项。

这类测试能验证游戏客户端的发现请求、公告接收与列表显示。它不能单独证明：

- 两个真实 Civ6 进程之间已完成加入和进入对局；
- Civ6 游戏数据面 62056 的双向转发正确；
- DLL 对异步/重叠 I/O、事件、WSAPoll、IOCP 等语义的覆盖完整；
- 不同 VPN 产品或跨 NAT 环境均可工作。

后续报告应分别标注“模拟房主→真实 Civ6 客户端”“真实双机 Civ6”“模拟数据面对端”，不得将三者合并成“联机通过”。

## 2. 目标架构

```text
Civ6 客户端
  ↕ Winsock 适配 DLL（Hook；保持原 API 语义）
本机 CivLink Agent
  ├─ 同网直连：WLAN / 已连接且可达的虚拟 LAN
  └─ 直连不可达：Relay
       ↕ 对端 Agent
对端适配 DLL / 游戏端
```

- **游戏适配 DLL**：Windows x64；先实现发现路径，再实现 62056 数据路径。不得在 Hook 内阻塞等待 Agent、同步写日志或破坏 Winsock 错误码与异步语义。
- **Agent**：独立进程，负责发现请求与房间公告的转发、Peer 会话、Fake-IP 映射、直连/Relay 路径选择和可观测计数。沿用 Rust 原型作为实现起点；最终本地 IPC 和 wire format 以测试结果定版。
- **Fake-IP**：保留为游戏数据面虚拟地址映射机制；地址池与生命周期必须通过独立实验确定，不预先写死旧设计中的候选段。
- **Relay**：保留为直连失败时的数据路径。服务端不解析游戏载荷；连接认证、完整性及加密策略需在协议设计任务中确定。
- **模拟房主**：作为本阶段自动化对端，可提供已知公告、请求/响应脚本、故障注入和可重复日志；模拟器不是产品 Relay，也不能代表真实 Civ6 房主。

## 3. 快速路线与退出条件

### F0：固定模拟房主基线

**交付**：一个可复现、带版本与哈希的 simulator 工具包；固定公告 fixture；逐请求、逐页、逐时间戳日志；失败时非零退出码。

**验证**：

- 模拟器能接收 Civ6 一次刷新中所有可监听发现请求，不因单次异常静默停止；
- 按限制发送完整公告页；每页长度、顺序、序号和摘要可核对；
- 至少连续 20 次刷新均按预期看到房间，清楚记录重复列表/超时/端口占用；
- 保留用户已反复验证的既有结果作为先验事实，同时新回归日志绑定具体二进制哈希。

失败则只修模拟器/测试夹具，不开始 DLL 数据面开发。

### F1：DLL + Agent 发现链路（一个真实 Civ6 客户端 + 模拟房主）

**交付**：最小 x64 Hook DLL、独立 Agent、明确版本的本机 IPC 帧；可观测请求接收、排队、转发、公告回送和游戏列表结果。

**验证**：

- Hook 命中正确发现 API；原始调用返回值、错误码、最后错误和 socket 生命周期保持正确；
- Hook 不阻塞、不静默丢包；本机通道发送/接收/确认/丢弃计数闭合；
- simulator 作为远端房主时，真实 Civ6 能稳定显示房间；关掉 Agent/DLL 时行为可解释并可恢复；
- 做短时重复刷新和异常退出测试；DLL/Agent 可干净停用。

这一步是首个产品集成门槛。若模拟房主仍能发现，但 Hook 接入后列表失败，优先定位 IPC 和 Winsock 语义，不扩大到 Relay 或 GUI。

### F2：Fake-IP 游戏数据面（一个真实 Civ6 客户端 + 模拟数据端）

**交付**：Fake-IP→Peer 映射表、会话代次与超时清理；Agent 的可配置 UDP 数据面；可注入丢包、乱序、重复、延迟的模拟端。

**验证**：

- DLL 到 Agent、Peer/模拟端到 Agent、Agent 到 DLL、DLL 到游戏的五类计数逐包对账；
- 对 62056 使用真实抓取到的 API/socket 模型，逐项覆盖阻塞/非阻塞、Overlapped、事件和轮询路径；
- 注入延迟/丢包后无卡死、无跨会话串包、无旧 Fake-IP 误投；关闭会话后资源归零；
- 所有错误可诊断，无法可靠交付时 fail-closed，不伪报成功。

模拟数据端可验证实现逻辑，但不能代替 Civ6 对端的真实协议和游戏行为验证。

### F3：直连与 Relay 路径

**交付**：Agent 的端到端路径状态机：发现候选→探测可达性→直连优先→超时转 Relay→恢复后切回或保持会话；状态可在 UI/日志查看。

**验证**：

- WLAN 直连 fixture；
- 虚拟 LAN 仅在客户端在线且 Peer 探测实际可达时判定为可用；不能仅凭网卡存在或 VPN 名称判定；
- 阻断直连时走 Relay；阻断 Relay 时明确失败；恢复网络后会话行为确定；
- Relay 仅转发不透明的认证数据；不得宣称“各种 VPN 都兼容”，只公布逐项验证过的环境。

本阶段可由模拟 Peer 与网络故障注入完成大部分工程验证；若要宣称真实两台 Civ6 经过 Relay 完成对局，仍需实际双游戏端或等效用户验收证据。

### F4：发布候选与单机验收

**交付**：Windows 安装/启动包、版本检测、日志导出、崩溃恢复、DLL 安全卸载、用户可见路径状态和已知限制。

**单机验收**：在一台 Steam Civ6 电脑上，用 simulator 做发现/公告/数据面的重复回归；稳定通过后可发布为**模拟对端/发现助手测试版**，不得标为“双人真实联机已通过”。

## 4. Gate 与旧计划关系

- 本路线**不再等待 PC-B Civ6 才开始 F0–F3 的工程开发**。
- 旧 M0-A/Gate A 的真实双机证据仍保留为“待验证”。模拟测试不能自动勾掉 Gate A 的 E2-A、E2-B 或 E3。
- DLL 绑定矩阵、Design I ≥1000 次确定性投递、Hook API 覆盖和真实游戏 socket 语义仍是发布前技术门槛；通过 simulator 可以先开发与缩小风险，不能绕过这些门槛。
- Fake-IP、Relay 保留在目标架构中；它们的首版实现顺序是 F2→F3，不提前做通用多人、跨平台或大规模服务。
- 用户提供的模拟器已可被 Civ6 搜到这一事实，不需要重复争论；新工作聚焦于把它纳入可重复回归，再尽快集成 DLL/Agent。

## 5. 暂不做

- 不等待第三台电脑，不再要求第二台 Civ6 电脑才可开始工程原型；
- 不把纯 mock UI、metric helper 或静态路由预测当产品核心；
- 不为“兼容所有 VPN”扩大首版范围；
- 不删除历史证据、旧 Gate 报告或规范。旧计划仅作为验收/历史材料；本文件仅更新工程推进顺序与开发夹具策略。
